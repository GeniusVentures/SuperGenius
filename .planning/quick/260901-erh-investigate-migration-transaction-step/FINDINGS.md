# Findings: Migration3_6_0To3_7_0 first-real-use investigation (260901-erh)

All paths relative to repo root. Line numbers verified against the working tree at commit ca6799f3 (branch gsd/phase-13-close-v1-1-trusted-peer-genesis-quorum-policy-and-production). Historical claims about 3.5.x cite `git show TestNet-Phase-3.520:<path>`.

## Trigger & Lifecycle Map

### 1. Exact upgrade flow for a 3.5.20 node moving to 3.7.0

Entry: `GeniusNode::New` unconditionally calls `BeginDBInitialization` (src/account/GeniusNode.cpp:146-156), which transitions to `NodeState::MIGRATING_DATABASE` (src/account/GeniusNode.cpp:580-583). The `MIGRATING_DATABASE` case starts the account messenger and calls `MigrateDatabase` with a completion callback (src/account/GeniusNode.cpp:614-640). `MigrateDatabase` constructs `MigrationManager::New` (passing `account_` and `node_type_`, src/account/GeniusNode.cpp:1905-1915) and runs `Migrate()` on a detached thread (src/account/GeniusNode.cpp:1923-1932).

Registered chain: 0.2.0->1.0.0->3.4.0->3.5.0->3.6.0->3.7.0 (src/migration/MigrationManager.cpp:46-84). `Migrate()` runs each step's `Init` -> `IsRequired` -> `Apply` -> `ShutDown` in one pass (src/migration/MigrationManager.cpp:103-124). Note: every `BOOST_OUTCOME_TRY` (src/migration/MigrationManager.cpp:110-123) returns early on failure, so an `Apply` failure **skips that step's `ShutDown`**; the step's members are cleaned up later only via their destructors (`~TransactionManager` calls `Stop()`, src/account/TransactionManager.cpp:323-328; `~GlobalDB` calls `ShutdownNow()`, src/crdt/globaldb/globaldb.cpp:107-120).

DB directories use path appendix `major.minor + net id` (src/base/sgns_version.cpp:68-73). Per step (all prefixed `SuperGNUSNode.Node`):

| Step | Legacy DB appendix | Target DB appendix | Evidence |
|---|---|---|---|
| 3.4.0->3.5.0 | (3,4) | (3,5) | src/migration/Migration3_4_0To3_5_0.cpp:426,459 |
| 3.5.0->3.6.0 | (3,5) | (3,6) | src/migration/Migration3_5_0To3_6_0.cpp InitLegacyDb/InitTargetDb (appendix 3,5 / 3,6) |
| 3.6.0->3.7.0 | (3,6) | (3,7) | src/migration/Migration3_6_0To3_7_0.cpp:532,565 |

For a 3.5.20 node upgrading to 3.7.0 (cmake/version.cmake:1 - PROJECT_VERSION 3.7.0):

1. 0.2.0->1.0.0 and 1.0.0->3.4.0 skip if their legacy DBs are absent (pattern of src/migration/Migration1_0_0To3_4_0.cpp IsRequired).
2. 3.4.0->3.5.0 skips: no (3,4) DB exists on a 3.5.20 install.
3. 3.5.0->3.6.0 runs: legacy (3,5) DB exists (its FromVersion() string is "3.5.1", src/migration/Migration3_5_0To3_6_0.cpp:43-47, but discovery is by the (3,5) path appendix, so 3.5.20 data qualifies); target (3,6) DB is created fresh; chain transactions for DEV/TEST/MAIN networks are copied into the (3,6) DB through real CRDT transactions with topics (src/migration/Migration3_5_0To3_6_0.cpp:100-182); the `kSGNSCRDTVersion` marker (src/migration/MigrationManager.hpp:92) is written as "3.6.0" via a **raw RocksDB put** (src/migration/Migration3_5_0To3_6_0.cpp:184-189).
4. 3.6.0->3.7.0 runs: legacy (3,6) DB now exists with version "3.6.0" < "3.7.0" (src/migration/Migration3_6_0To3_7_0.cpp:88-123), target (3,7) DB is created fresh, and `Apply()` executes the full claim path (src/migration/Migration3_6_0To3_7_0.cpp:137-351). On success it writes `kSGNSCRDTVersion = "3.7.0"` (src/migration/Migration3_6_0To3_7_0.cpp:343-347).

### 2. Which node types reach `Migration3_6_0To3_7_0::Apply`

There is **no `node_type_` branch anywhere in `Apply()`** (src/migration/Migration3_6_0To3_7_0.cpp:137-351); `node_type_` is only forwarded to `Blockchain::New` (line 180) and `TransactionManager::New` (line 292). Every node type (Full/Light/Archive) enters `MIGRATING_DATABASE` via the same unconditional `GeniusNode::New` path (src/account/GeniusNode.cpp:153), and Archive nodes are exercised through the whole chain by migration_sync_test (test/src/transaction_sync/migration_sync_test.cpp:247-307).

What each type claims: `ComputeLegacyBalances` reconstructs balances for **all addresses present in that node's own (3,6) DB** (src/migration/Migration3_6_0To3_7_0.cpp:445-524). The (3,6) DB only contains what the node replicated on 3.5.x (a Full/Archive node replicates everything; a Light node replicates only its own account's data - src/account/NodeType.hpp:27,39-48 - and the (3,5)->(3,6) copy at src/migration/Migration3_5_0To3_6_0.cpp:109-176 can only copy what exists locally). A Light node therefore typically sees only its own address's balance, submits its own claim (src/migration/Migration3_6_0To3_7_0.cpp:271-325), and has a complete-enough view for its own funds because its spending transactions are its own (source-address topics). A node with **no** observed balance skips the claim and just writes the version marker (src/migration/Migration3_6_0To3_7_0.cpp:278,338-341).

Gate needed? No `node_type_` gate is required for claim correctness: a Light node's claim is bounded by the remote allow-list gate at 2x observed balance (src/account/MigrationAllowList.cpp:85-103; src/account/TransactionManager.cpp:3806-3823), and excluding Light nodes would strand their funds. The Light/Full split matters instead for **validation coverage** (thread 2b): a Light validator cannot approve anyone else's claim because its allow-list only contains its own address.

### 3. Failure taxonomy of `Apply()` and node-level behavior

| # | Failure point in Apply() | Error returned | Node behavior |
|---|---|---|---|
| i | Target DB not initialized | std::errc::no_such_device (src/migration/Migration3_6_0To3_7_0.cpp:144-148) | Callback logs error, no retry, no state advance (src/account/GeniusNode.cpp:627-636) |
| ii | Blockchain::MigrateCids / StartCICSync errors | propagated raw (src/migration/Migration3_6_0To3_7_0.cpp:155-158) | same as (i) |
| iii | Blockchain start retry exhausted / status wait timeout | BLOCKCHAIN_INIT_FAILED (src/migration/Migration3_6_0To3_7_0.cpp:185-239) | **Retries**: callback matches the error (src/account/GeniusNode.cpp:630-634) -> ScheduleMigrationRetry (src/account/GeniusNode.cpp:1935-1947) re-transitions to MIGRATING_DATABASE after 5 s |
| iv | Genesis/account-creation/validator-registry wait timeout | BLOCKCHAIN_INIT_FAILED (src/migration/Migration3_6_0To3_7_0.cpp:241-260) | retries as (iii) |
| v | Transaction Manager did not reach READY in 4 min | BLOCKCHAIN_INIT_FAILED (src/migration/Migration3_6_0To3_7_0.cpp:300-313) | retries as (iii) |
| vi | Claim submission error (MigrationFunds) | propagated raw (src/migration/Migration3_6_0To3_7_0.cpp:321-325) | same as (i) |
| vii | Claim not CONFIRMED within 4 min | std::errc::timed_out (src/migration/Migration3_6_0To3_7_0.cpp:328-336) | **No retry, no state advance** - see below |

Confirmed: only BLOCKCHAIN_INIT_FAILED is matched in the MigrateDatabase callback (src/account/GeniusNode.cpp:627-635); every other error - including timed_out - logs "Database migration error" and returns (src/account/GeniusNode.cpp:629,635).

User-visible consequence of (vii): the callback returns without any transition, so state_ remains MIGRATING_DATABASE forever (the only path out is the success branch at src/account/GeniusNode.cpp:637). The node never initializes its real GlobalDB/blockchain/transaction services (those are entered from INITIALIZING_DATABASE onward, src/account/GeniusNode.cpp:642-651), keeps the migration-time blockchain_/transaction_manager_/GlobalDB instances alive (the step's ShutDown was skipped by the BOOST_OUTCOME_TRY early return, src/migration/MigrationManager.cpp:116), and the only remedy is a manual process restart - which re-runs the migration and, per thread 2c, can deterministically fail forever after a late-confirming first claim.

### 4. Re-run semantics after a failed/interrupted run

The version marker is written only on full success (src/migration/Migration3_6_0To3_7_0.cpp:343-347), so IsRequired() keeps returning true (src/migration/Migration3_6_0To3_7_0.cpp:102-123: no version info in the (3,7) DB -> required). On the next Migrate() pass, earlier steps skip via their own markers/absent legacy DBs (e.g. src/migration/Migration3_5_0To3_6_0.cpp:59-77), and the 3_6->3_7 step re-runs Apply() end-to-end: CID migration again (src/migration/Migration3_6_0To3_7_0.cpp:155), balances recomputed (line 263), the allow-list **re-stored with identical values** (idempotent raw-key overwrites, lines 264-265; src/account/MigrationAllowList.cpp:35-50), and a **new** claim submitted (lines 321-325) whose hash differs from the previous attempt - FillDAGStruct embeds a fresh timestamp and reserved nonce (src/account/TransactionManager.cpp:1250-1270) - while the synthetic one-time input stays byte-identical (src/account/MigrationTransaction.cpp:199-226).

## First-Run Risk Analysis

### (a) Confirmation timing under real consensus/finality

Path to CONFIRMED: MigrationFunds builds and signs a MigrationTransaction and enqueues it (src/account/TransactionManager.cpp:773-793 -> 1223-1242). The READY-state worker sends it via SendTransactionItem (src/account/TransactionManager.cpp:531-568): the tx is persisted through a CRDT transaction and a consensus proposal is created (CreateConsensusProposal call in SendTransactionItem; builder at src/blockchain/Consensus.cpp:1031-1036). Status becomes CONFIRMED only when a quorum certificate validates (OnConsensusCertificate, src/account/TransactionManager.cpp:3463-3613; "Transaction {} confirmed by consensus" at 3580). Rounds are fast (default round duration 500 ms, src/blockchain/Consensus.hpp:608) and quorum is weight-based over the validator registry (src/blockchain/Consensus.cpp:1308-1390). WaitForTransactionOutgoing is terminal on CONFIRMED/UNCONFIRMED/INVALID/FAILED (src/account/TransactionManager.cpp:2302-2307) and otherwise returns whatever it last saw at the 4-minute deadline (src/account/TransactionManager.cpp:2309).

Against the fixed budgets in Apply() - 2-min blockchain-start retry (src/migration/Migration3_6_0To3_7_0.cpp:185-207), 4-min status wait (209-239), 4-min genesis/registry wait (241-260), 4-min TM-READY wait (300-313), 4-min confirmation wait (328) - a healthy-but-slow forming network fails the **earlier** gates first with BLOCKCHAIN_INIT_FAILED, which self-heals via the 5-second node-level retry (src/account/GeniusNode.cpp:630-634,1935-1947). The dangerous window is the last one: TM READY but the claim cannot certify within 4 minutes (quorum absent, or validators rejecting per thread (b)). That failure is timed_out, which gets **no retry and wedges the node in MIGRATING_DATABASE** (Task 1, row vii). The 3.5.x testnet never exercised this because it had no consensus/finality at all.

Verdict: ADJUST - a 4-minute budget is adequate for 500 ms rounds once quorum exists, but the missing node-level retry for timed_out turns any slow first confirmation into a permanent wedge; schedule a migration retry for it (same mechanism as BLOCKCHAIN_INIT_FAILED).

### (b) Cross-node allow-list convergence

Writes do **not** propagate. Apply() constructs the allow-list over `db_3_7_0_->GetDataStore()` (src/migration/Migration3_6_0To3_7_0.cpp:264), and GetDataStore() returns the **raw RocksDB** handle m_datastore (src/crdt/globaldb/globaldb.hpp:159; src/crdt/globaldb/globaldb.cpp:716-720). StoreObservedBalance does a plain raw `db_->put` of `/migration-allowlist/<version>/<address>` (src/account/MigrationAllowList.cpp:35-50; key builder 147-155). The only network-propagated write path is CrdtDatastore::PutKey, which creates a delta and publishes it (src/crdt/globaldb/globaldb.cpp:527-537; src/crdt/impl/crdt_datastore.cpp:1330-1341), and merged CRDT values live under internal /namespace/s/... and /namespace/k/... keys (src/crdt/impl/crdt_set.cpp:691-703,638-645) - a raw put never becomes a delta, and a CRDT-merged value is never visible at the raw key path. A repo-wide grep confirms MigrationAllowList has exactly two users: the migration step (write) and the consensus gate (read) - no other propagation mechanism exists (src/account/TransactionManager.cpp:3808; src/migration/Migration3_6_0To3_7_0.cpp:264).

Remote gate behavior: every validator runs HandleNonceConsensusSubject, builds a local allow-list over its own raw store (src/account/TransactionManager.cpp:3806-3809), and a missing entry makes IsEligible return false (src/account/MigrationAllowList.cpp:92-96) -> reject_and_maybe_fail_local("migration source address not locally eligible") (src/account/TransactionManager.cpp:3819-3822; lambda at 3732-3773). A Reject is not a network-wide veto: reject votes simply add no weight, and the proposal certifies only if quorum **approving** weight is reached (src/blockchain/Consensus.cpp:1355-1380). A locally dropped proposal is not re-proposed by consensus (Reject -> "rejected: subject check failed" and return, src/blockchain/Consensus.cpp:1656-1663); on the claiming node the outgoing tx eventually resolves to a terminal state via the proposal-timeout cleanup path or the reject handling itself, and WaitForTransactionOutgoing then returns non-CONFIRMED (src/account/TransactionManager.cpp:2302-2307).

Conclusion: claim confirmation does not depend on a timing race - it depends on whether the **quorum-weight validators each independently observed the claiming address's balance in their own legacy (3,6) DB**. All 3.5.x-era nodes were full replicators (in-memory UTXO map, full chain data; the Light/Full/Archive split postdates 3.5.20 - src/account/NodeType.hpp:3-8), so upgraded validators from 3.5.20 hold converging, complete allow-lists. But **fresh 3.7.0 genesis validators** (the v1.1 trusted-peer ceremony model) have empty allow-lists and reject every migration claim; with such a validator set, no migration claim can certify, ever, within any budget. The proposed small fix (missing entry -> Pending(), src/account/TransactionManager.cpp:3819-3822) would not help: pending entries expire after a 3-minute TTL with no convergence mechanism to wake them (src/blockchain/Consensus.hpp:206-216; expiry path src/blockchain/Consensus.cpp:1004-1029), and it would weaken overclaim rejection (T-QUICK-02) by stalling genuinely ineligible claims for 3 minutes instead of rejecting them.

Verdict: ADJUST - allow-list observations must become network-visible (CRDT-published entries or genesis-seeded allow-lists) before mainnet 3.7.0 launches with fresh genesis validators; this is a design-level change (out of small-fix scope) and the Pending() patch is explicitly rejected.

### (c) Double-claim and idempotency on retry

One-time key: DeriveUniqueSourceKey hashes (from_version, source_address, token_id) (src/account/MigrationTransaction.cpp:199-205) and installs the result as both the synthetic consumed input and the uncle hash (src/account/MigrationTransaction.cpp:218-226); MigrationInputValidator::ValidateWitness rejects any migration subject whose input/uncle/amount/token do not match the derived key and whose UTXO commitment does not bind exactly one consumed outpoint and one produced output (src/account/MigrationInputValidator.cpp:56-117, key check 68-77).

Retry produces a **new** tx hash (fresh timestamp + reserved nonce via FillDAGStruct, src/account/TransactionManager.cpp:1254-1267) with the **same** synthetic outpoint. If the first claim is CONFIRMED anywhere in a validator's tracked set, the re-claim is rejected as an input conflict before the allow-list gate is even reached (HasConfirmedInputConflict, src/account/TransactionManager.cpp:3386-3431, invoked at 3793-3797) - double minting is prevented (T-QUICK-01 mitigated). Two simultaneously *pending* claims (crash between submit and confirm, then retry) are both structurally valid subjects; whichever certifies first wins, and the loser is then rejected at 3793 - no double mint, one cert.

Liveness gap: if run 1's claim confirms **after** run 1's 4-minute window expired, every subsequent run re-submits a fresh claim that is deterministically rejected against the confirmed first claim (the node reloads its own confirmed transactions into tx_processed_m at startup - InitTransactions/LoadUTXOs, src/account/TransactionManager.cpp:516-522,2386), so Apply() fails forever and the version marker is never written (src/migration/Migration3_6_0To3_7_0.cpp:321-347 has no "already claimed" check). The funds are migrated but the node can never complete migration without manual DB surgery.

Verdict: NO-ADJUST - the one-time-key + input-conflict design correctly prevents double minting on all retry orderings; the residual liveness gap (skip re-claim when a confirmed claim already exists) is a follow-up item, not a pre-release safety defect.

### (d) Balance coverage policy for mainnet 3.5.20 data

Snapshot branch is dead code for 3.5.x: 3.5.20's UTXOManager kept balances purely in memory (std::unordered_map utxos_, `git show TestNet-Phase-3.520:src/account/UTXOManager.hpp:104-105`; no "/utxo/" string anywhere in the tag's src). So ComputeLegacyBalances always falls through to reconstruction (src/migration/Migration3_6_0To3_7_0.cpp:430-439) over the chain `tx` entries that 3_5->3_6 copied into the (3,6) DB for all three networks (src/migration/Migration3_5_0To3_6_0.cpp:105-176; monitored networks narrowed per node at src/account/TransactionManager.cpp GetMonitoredNetworkIDs - mainnet nodes see only mainnet txs).

Type coverage: reconstruction handles any transaction exposing UTXO parameters - current registry: transfer, mint-v2, mint, migration, escrow-hold, escrow-release (src/account/TransactionManager.cpp:1703-1708; UTXO-parameter providers in src/account/EscrowTransaction.hpp, MintTransactionV2.hpp, TransferTransaction.hpp, MigrationTransaction.hpp) - plus v1 MintTransaction by dynamic cast (src/migration/Migration3_6_0To3_7_0.cpp:487-492). 3.5.20's transaction types were transfer, mint, escrow-hold, escrow-release, process (registered in each tag header, e.g. `git show TestNet-Phase-3.520:src/account/ProcessingTransaction.hpp`). The only type with no current deserializer is "process", and 3_5->3_6 skips undecodable entries with a log (src/migration/Migration3_5_0To3_6_0.cpp:133-138); the 3.5.20 ProcessingTransaction carried no value (job/subtask metadata only - tag header), so nothing is lost. All 3.5.x value shapes (transfer, mint, escrow-hold, escrow-release) are covered.

Two policy consequences:

1. Reconstruction trusts the unfinalized 3.5.x ledger as-is: consumed_outpoints marks an outpoint spent regardless of which conflicting spend "won" (src/migration/Migration3_6_0To3_7_0.cpp:471-475), while outputs of losing double-spend txs still credit their recipients (477-482). On a chain that had no finality this can over-credit balances; the remote allow-list gate (2x cap + validator-side observation) is the only bound. Inherent to migrating unfinalized data - documented, not small-fixable.
2. IsMigratableBalanceAddress accepts only 128-char lowercase-hex account addresses (src/migration/Migration3_6_0To3_7_0.cpp:50-53; src/account/UTXOStructs.cpp:32-37; src/base/hexutil.cpp:37-47). Escrow **lock** addresses ("0x" + 64 hex, src/account/UTXOStructs.cpp:22-30) are silently dropped, so funds locked in unreleased escrows at upgrade time are not migrated. Lock addresses are not backed by any private key, so no one could claim them anyway; released escrows credit the release destination normally. Acceptable as policy, but must be a conscious release decision.

Verdict: NO-ADJUST - reconstruction covers every 3.5.x value-carrying transaction type; the escrow-lock exclusion and unfinalized-ledger inflation are policy risks to document, not code defects fixable within scope.

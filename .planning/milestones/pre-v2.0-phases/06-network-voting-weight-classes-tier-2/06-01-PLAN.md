<objective>
Establish the cryptographic foundation of the slot-based RPC-hash voting model (D-01). Extend the `ConsensusVote` proto with three slot-hash fields, add endpoint-hashing accessors to `PublicChainInputValidator`, and wire slot-hash population into `ConsensusManager::CreateVote` via a callback injected by `GeniusNode`.

**Replanned 2026-06-19** after codebase research revealed the actual architecture:
- Votes are created in `ConsensusManager::CreateVote()` at `Consensus.cpp:1155`, NOT in `GeniusNode`
- `PublicChainInputValidator` is owned by `TransactionManager`, NOT `GeniusNode`
- `WeightedRpcEndpoint` has no `is_paid`/`api_key_*` fields — classification is by `consensus_weight` numeric threshold (≥50 = DIRECT_API slot 0, <50 = PUBLIC slots 1-2)
- The bridge between the two sides is `GeniusNode`, which has access to both `blockchain_` (→ `consensus_manager_`) and `transaction_manager_` (→ `PublicChainInputValidator`)

Purpose: Without slot-hash fields in the proto and the signing surface, no later tally can deduplicate by hash (D-03) or attribute 50/25 weight (D-02). Plan 02 consumes the fields. Plan 03 (FULL promotion) is independent.

Output:
- `Consensus.proto` with `slot_0_hash`, `slot_1_hash`, `slot_2_hash` on `ConsensusVote`.
- `PublicChainInputValidator::GetSlotHash(slot_index, chain_id)` that returns SHA-256 of the endpoint URL.
- `ConsensusManager::SetSlotHashPopulator(callback)` + invocation in `CreateVote` before signing.
- `GeniusNode` wiring during blockchain init.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GeniusNode → ConsensusManager callback injection | The populator bridges two subsystems; a miswired callback could populate wrong hashes. Mitigated by the callback being set once at init time by GeniusNode, which owns both sides. |
| Node → Network (vote broadcast) | Outgoing `ConsensusVote` crosses this boundary; the slot hashes must be committed under the vote signature so peers can detect tampering. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Tampering | ConsensusVote slot hashes | mitigate | Slot hashes are inside the `VoteSigningBytes` signing surface (only `signature` is cleared). Any mutation invalidates the signature. |
| T-06-02 | Spoofing | SlotHashPopulator callback | mitigate | The callback is set once at init by GeniusNode (trusted boot path). An attacker would need code execution to replace it. |
| T-06-03 | Information Disclosure | GetSlotHash URL hashing | accept | The hash is SHA-256 of the URL template; it does not reveal API keys (none exist in WeightedRpcEndpoint). |
| T-06-04 | Repudiation | Empty-bytes abstain sentinel | mitigate | Empty slot hashes are explicitly documented as abstention (D-05). |
| T-06-SC | Tampering | No third-party packages installed | accept | Pure proto + internal-hasher change; no npm/pip/cargo. |
</threat_model>

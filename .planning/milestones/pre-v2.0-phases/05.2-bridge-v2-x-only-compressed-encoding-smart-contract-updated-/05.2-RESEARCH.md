# Phase 05.2: Bridge V2 -- X-only Compressed Encoding - Research

**Researched:** 2026-06-18
**Domain:** secp256k1 elliptic curve cryptography, ABI event decoding, bridge event processing
**Confidence:** HIGH

## Summary

Phase 05.2 upgrades the bridge pipeline from full 64-byte uncompressed SuperGenius public keys to 32-byte X-only compressed keys. The EVM contract event changes from `BridgeSourceBurned(address,uint256,uint256,uint256,uint256,bytes)` to `BridgeOutInitiated(address,uint256,uint256,uint256,uint256,bytes32,bool)`. The C++ side must decompress the X-only key to full X+Y to construct the 128-char hex destination string that `GetAddress()` returns.

The research identified three C++ subsystems requiring changes: (1) the `EventRegistry` in `evmrelay` to register the new event signature, (2) `BridgeRelayer::OnWatchEvent()` to handle both v1 and v2 event formats with X-only decompression, and (3) `GeniusNode::PerformStartupCatchupScan()` to query both v1 and v2 topic0 hashes. The `BridgeRpcWatcher` in `src/watcher/` does NOT need changes -- it uses configurable event signatures and does not decode ABI params for destination.

The **Y parity is explicit (D-09):** the contract event includes `bool destinationYOdd` — `false` = even Y (0x02 prefix), `true` = odd Y (0x03 prefix). The C++ decompression uses this directly: `uint8_t prefix = destinationYOdd ? 0x03 : 0x02;`. Parse the 33-byte compressed key via libsecp256k1, serialize uncompressed, extract `uncompressed[1..64]` (skip 0x04 prefix) as the 64-byte raw public key. No convention enforcement needed — the event data carries the ground truth. No dual-parity trial needed.

**Primary recommendation:** Use the existing `libsecp256k1` library (already linked in evmrelay) for X-only decompression. Use the even-Y prefix (0x02) exclusively per the locked system convention. Decompress via `secp256k1_ec_pubkey_parse` + `secp256k1_ec_pubkey_serialize`, and construct the full 128-char destination string. Add the decompression as a free function in `evmrelay/include/eth/secp256k1_utility.hpp` following project conventions.

### Pattern 1: Versioned Event Dispatch in OnWatchEvent
**What:** `BridgeRelayer::OnWatchEvent()` dispatches on event signature (or param count/types) to handle v1 (6 params, ByteBuffer) vs v2 (7 params, Hash256 + bool) event formats.
**When to use:** When a single callback receives events from multiple registered watches with different ABI signatures.
**Example:**
```cpp
// Source: Derived from existing BridgeRelayer::OnWatchEvent() structure
void BridgeRelayer::OnWatchEvent(const eth::WatchEventNotification& notification,
                                  const std::string& chain_name)
{
    static constexpr size_t kParamCount = 6;
    if (notification.values.size() < kParamCount) { /* error */ return; }

    // Dispatch on value type at position 5
    if (std::holds_alternative<eth::codec::ByteBuffer>(notification.values[5]))
    {
        // V1: full 64-byte destination
        ProcessV1Burn(notification, chain_name);
    }
    else if (std::holds_alternative<eth::codec::Hash256>(notification.values[5]))
    {
        // V2: 32-byte X-only key -- decompress
        ProcessV2Burn(notification, chain_name);
    }
}
```

### Pattern 2: secp256k1 Compressed-to-Uncompressed Decompression
**What:** Standard libsecp256k1 pattern used throughout evmrelay (discv5, discv4, rlpx, secp256k1_utility).
**When to use:** Whenever a compressed 33-byte public key (02/03+X) needs to be expanded to 65-byte uncompressed form.
**Example:**
```cpp
// Source: evmrelay/src/eth/secp256k1_utility.cpp:30-51 (address_from_public_key)
// Adapted for X-only decompression with explicit parity from bool
std::optional<std::array<uint8_t, 65>> DecompressKey(
    const std::array<uint8_t, 32>& x_bigendian, uint8_t prefix_byte)
{
    secp256k1_context* ctx = secp256k1_context_create(SECP256K1_CONTEXT_NONE);
    if (!ctx) { return std::nullopt; }

    // Build 33-byte compressed key: [prefix][X(32 bytes)]
    std::array<uint8_t, 33> compressed{};
    compressed[0] = prefix_byte; // 0x02 or 0x03 from bool destinationYOdd
    std::copy(x_bigendian.begin(), x_bigendian.end(), compressed.begin() + 1);

    secp256k1_pubkey pubkey{};
    if (!secp256k1_ec_pubkey_parse(ctx, &pubkey, compressed.data(), compressed.size()))
    {
        secp256k1_context_destroy(ctx);
        return std::nullopt;
    }

    std::array<uint8_t, 65> uncompressed{};
    size_t len = uncompressed.size();
    secp256k1_ec_pubkey_serialize(ctx, uncompressed.data(), &len,
                                   &pubkey, SECP256K1_EC_UNCOMPRESSED);
    secp256k1_context_destroy(ctx);
    return uncompressed; // [04][X_bigendian][Y_bigendian]
}
```

### Pattern 3: Two-Query Catch-Up Scan for Multiple Topic0 Hashes
**What:** Since `EventFilter::topics` uses single-value-per-position semantics (no OR support in serialization), make two separate `eth_getLogs` calls and merge results.
**When to use:** When the catch-up scan must find both v1 and v2 burns from historical blocks.
**Example:**
```cpp
// Source: Adapted from GeniusNode::PerformStartupCatchupScan()
// Query 1: v1 burns
std::string topic0_v1 = compute_topic0("BridgeSourceBurned(...)");
auto logs_v1 = query_get_logs(transport, contract, topic0_v1, from_block, to_block);

// Query 2: v2 burns
std::string topic0_v2 = compute_topic0("BridgeOutInitiated(...)");
auto logs_v2 = query_get_logs(transport, contract, topic0_v2, from_block, to_block);

// Merge and deduplicate by tx_hash
std::set<std::string> seen;
for (auto& log : logs_v1) { process_and_dedup(log, seen); }
for (auto& log : logs_v2) { process_and_dedup(log, seen); }
```

### Anti-Patterns to Avoid
- **Hand-rolling modular square root:** Do NOT implement y = sqrt(x^3 + 7 mod p) manually. Use libsecp256k1's `secp256k1_ec_pubkey_parse` which handles this natively and has been audited. Hand-rolling introduces cryptographic implementation risks (timing side-channels, incorrect modular arithmetic).
- **Ignoring the bool destinationYOdd parameter:** Do NOT hardcode a single parity prefix. Use the `destinationYOdd` bool from the event to select 0x02 (false) or 0x03 (true). The parity is explicit in the event data.
- **Blocking catch-up scan on both topic0 queries:** Two sequential `eth_getLogs` calls are acceptable (each ~100-500ms). Do not add artificial delays or complex synchronization. Simple sequential calls with merged result sets suffice.
- **Duplicating decompression logic:** Implement decompression ONCE in evmrelay (near existing secp256k1 utilities). Both `BridgeRelayer` and `GeniusNode` call the same free function.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| secp256k1 point decompression (X → Y recovery) | `y = sqrt(x^3 + 7 mod p)` via manual modular square root | `secp256k1_ec_pubkey_parse()` with 33-byte compressed key | libsecp256k1 is audited, constant-time, handles all edge cases (point at infinity, invalid X not on curve). Already linked in evmrelay. |

**Key insight:** libsecp256k1 already provides `secp256k1_ec_pubkey_parse` which accepts compressed 33-byte public keys and internally performs the modular square root to recover Y. The entire decompression is a single library call. No custom cryptography is needed.

## Byte Ordering Reference

The key challenge in this phase is byte ordering between three different representations:

| Layer | Format | Byte Order | Example |
|-------|--------|------------|---------|
| Internal (X_vect/Y_vect) | `std::vector<uint8_t>` (32 bytes) | Big-endian (MSB first) | X_vect[0] = MSB of X |
| `util::to_string()` | Hex string (64 chars per coordinate) | Reverse (iterates rbegin→rend) | Last byte → first hex pair |
| `GetAddress()` = `util::to_string(X_vect) + util::to_string(Y_vect)` | 128 hex chars | Reverse X then reverse Y | `hex_bytes(GetAddress())` recreates contract bytes |
| `rlp::base::parse::hex_bytes(data, N)` | Forward hex conversion | data[0] → first hex pair | Used to convert contract bytes back to hex |
| Contract bytes (ABI) | 32 bytes (bytes32) or 64 bytes (bytes) | Reverse of X_vect byte order | byte[0] = X_vect[31] (LSB of X) |
| libsecp256k1 compressed | 33 bytes: [02/03][X_bigendian] | Big-endian X | X[0] = MSB |
| libsecp256k1 uncompressed | 65 bytes: [04][X_bigendian][Y_bigendian] | Big-endian X, big-endian Y | output[1..33] = X, output[33..65] = Y |

**Decompression byte flow:**
```
Contract bytes32 X (32 bytes, reverse order)
  → reverse to big-endian
  → [0x02][X_bigendian] (33 bytes compressed)
  → secp256k1_ec_pubkey_parse → pubkey object
  → secp256k1_ec_pubkey_serialize(UNCOMPRESSED) → [04][X_bigendian][Y_bigendian] (65 bytes)
  → extract Y_bigendian (bytes 33..65)
  → reverse Y_bigendian to contract byte order
  → hex_bytes(contract_X, 32) + hex_bytes(contract_Y, 32) = 128-char destination
  → matches GetAddress()
```

## Common Pitfalls

### Pitfall 1: Byte Order Reversal in Decompression
**What goes wrong:** Decompressing from contract X bytes without byte-order reversal produces a different X coordinate, causing Y to not match the account's key.
**Why it happens:** Contract bytes are stored in "util::to_string" reverse order (LSB first in hex). libsecp256k1 expects big-endian (MSB first). Failing to reverse produces a completely different field element.
**How to avoid:** Always reverse the 32 contract bytes before prepending the 02/03 prefix. After decompression, reverse Y_bigendian before converting to hex with `hex_bytes()`.
**Warning signs:** Destination hex doesn't start with the same 64 chars as the X from the contract event, or MintFunds destination mismatch.

### Pitfall 2: Wrong ABI Variant Access (std::bad_variant_access)
**What goes wrong:** Accessing `values[5]` with `std::get<ByteBuffer>` when the event format is v2 (Hash256), or vice versa.
**Why it happens:** The ABI decoder chooses the variant type based on `AbiParamKind`. kBytes → ByteBuffer, kBytes32 → Hash256. A watch registered with the wrong param kind will produce a value of the wrong type.
**How to avoid:** Use `std::holds_alternative<T>()` dispatch in `OnWatchEvent()` to handle both types, or check the event signature to determine the format. Register watches with correct param kinds per event.
**Warning signs:** `std::bad_variant_access` exception at runtime when processing bridge events.

### Pitfall 3: Catch-Up Scan Missing v2 Burns
**What goes wrong:** `PerformStartupCatchupScan()` only queries the v1 topic0 hash, missing v2 burns that were emitted after the contract upgrade.
**Why it happens:** The catch-up scan currently hardcodes one event signature. Adding a second query is needed but easy to overlook.
**How to avoid:** Make two `eth_getLogs` calls (one per topic0 hash), merge results, deduplicate by tx_hash.
**Warning signs:** Historical v2 burns not backfilled after node restart; users report missing bridge mints for transactions confirmed after contract upgrade.

### Pitfall 4: Y Parity Mismatch (explicit parity — bool in event)
**What goes wrong:** If the C++ side ignores or misreads the `destinationYOdd` bool, the wrong parity prefix is used, producing a Y coordinate that doesn't match the intended recipient's public key. This creates a UTXO with an incorrect destination.
**Why it could happen:** The ABI decoder must correctly extract both `bytes32 sgnsDestination` (param 5) and `bool destinationYOdd` (param 6) from the event data. A typo or off-by-one in the param index would read the wrong value.
**How to avoid:** Always read `destinationYOdd` from `values[6]` (or decoded[5] in non-indexed). Pass it directly to `DecompressXOnlyPubkey(x_bytes, destination_y_odd)`. The function uses the bool to select 0x02/0x03 prefix deterministically. Test both even-Y and odd-Y known vectors.
**Warning signs:** MintFunds creates transactions with destination that doesn't match any known account; `DecompressXOnlyPubkey` returns nullopt for valid X with wrong parity; catch-up scan silently produces incorrect destinations for v2 burns.

### Pitfall 5: Thread Safety with Event Callbacks
**What goes wrong:** `OnWatchEvent` is called from the EthWatchService thread. If decompression or MintFunds is not thread-safe, data races occur.
**Why it happens:** BridgeRelayer callbacks are invoked from the watch service's internal thread. The existing code already handles this for v1, but adding decompression (which creates/destroys secp256k1 contexts) must not introduce thread-safety issues.
**How to avoid:** Create and destroy secp256k1 contexts locally within the decompression call (no shared context). The existing pattern in `secp256k1_utility.cpp` already does this -- each function creates its own context.
**Warning signs:** Occasional crashes in secp256k1 functions, data corruption in destination strings, non-deterministic behavior.

### Decompression with Even-Y (0x02) Prefix
```cpp
// Source: Adapted from evmrelay/src/eth/secp256k1_utility.cpp and
//         evmrelay/src/discv5/discv5_client.cpp:164-182
// Verified: libsecp256k1 API via existing codebase usage patterns

#include <secp256k1.h>
#include <array>
#include <optional>
#include <string>

/// @brief Try decompressing X with a given prefix byte.
/// @return Uncompressed 65-byte key [04][X][Y] or nullopt on failure.
[[nodiscard]] std::optional<std::array<uint8_t, 65>> DecompressWithPrefix(
    const std::array<uint8_t, 32>& x_bigendian, uint8_t prefix)
{
    secp256k1_context* ctx = secp256k1_context_create(SECP256K1_CONTEXT_NONE);
    if (!ctx) { return std::nullopt; }

    std::array<uint8_t, 33> compressed{};
    compressed[0] = prefix;
    std::copy(x_bigendian.begin(), x_bigendian.end(), compressed.begin() + 1);

    secp256k1_pubkey pubkey{};
    if (!secp256k1_ec_pubkey_parse(ctx, &pubkey, compressed.data(), compressed.size()))
    {
        secp256k1_context_destroy(ctx);
        return std::nullopt;
    }

    std::array<uint8_t, 65> uncompressed{};
    size_t len = uncompressed.size();
    secp256k1_ec_pubkey_serialize(ctx, uncompressed.data(), &len,
                                   &pubkey, SECP256K1_EC_UNCOMPRESSED);
    secp256k1_context_destroy(ctx);
    return uncompressed;
}

/// @brief Decompress a 32-byte X-only key to full 128-char hex destination.
///        Always uses even-Y (0x02) prefix per system convention.
/// @param contract_x_bytes  32 bytes from the ABI-decoded bytes32 parameter.
/// @return 128-char hex destination string, or nullopt if decompression fails.
[[nodiscard]] std::optional<std::string> DecompressXOnlyPubkey(
    const std::array<uint8_t, 32>& contract_x_bytes)
{
    // Contract bytes are in "reverse" order (hex_bytes compatible).
    // Reverse to big-endian for secp256k1.
    std::array<uint8_t, 32> x_bigendian{};
    for (size_t i = 0; i < 32; ++i)
    {
        x_bigendian[i] = contract_x_bytes[31 - i];
    }

    // The X hex string (first 64 chars of destination) comes from
    // the contract bytes directly.
    std::string x_hex = rlp::base::parse::hex_bytes(
        contract_x_bytes.data(), contract_x_bytes.size());

    // Use even-Y prefix (0x02) per locked system convention
    constexpr uint8_t kEvenYParityPrefix = 0x02;
    auto uncompressed = DecompressWithPrefix(x_bigendian, kEvenYParityPrefix);
    if (!uncompressed) { return std::nullopt; }

    // uncompressed = [04][X_bigendian(32)][Y_bigendian(32)] = 65 bytes
    // Extract Y_bigendian (bytes 33..64) and reverse for contract order
    std::array<uint8_t, 32> contract_y{};
    for (size_t i = 0; i < 32; ++i)
    {
        contract_y[i] = (*uncompressed)[64 - i]; // bytes 64 down to 33, reversed
    }

    std::string y_hex = rlp::base::parse::hex_bytes(
        contract_y.data(), contract_y.size());

    // Construct full 128-char destination.
    return x_hex + y_hex;
}
}
```

## Open Questions (RESOLVED)

1. **Y parity disambiguation when the destination account is not locally known** — RESOLVED (explicit bool in event)
   - What we know: The contract now emits `bool destinationYOdd` in the event alongside `bytes32 sgnsDestination`. The bool directly signals the Y parity.
   - What was unclear: How does a validator node determine the correct Y without a locally known account?
   - **Resolution:** The `bool destinationYOdd` in `BridgeOutInitiated` provides the parity explicitly. The C++ side reads `values[6]` (or non-indexed decoded[5]) as a bool and passes it to `DecompressXOnlyPubkey(x_bytes, destination_y_odd)`. The function uses `destinationYOdd ? 0x03 : 0x02` to select the correct prefix. No convention enforcement, no trial-and-error, no destination matching required. This is the definitive resolution — the event carries the ground truth.

2. **Link dependency: can `src/account/` link `libsecp256k1::secp256k1`?** — RESOLVED
   - What we know: `libsecp256k1` is linked throughout evmrelay (`eth`, `rlp`, `discv4`, `discv5`, `rlpx`). The `secp256k1_utility.cpp` file is part of the `eth` target.
   - What's unclear: Whether the SuperGenius build (which links evmrelay as a dependency) can directly call libsecp256k1 functions from `src/account/`, or whether the decompression utility must be placed inside evmrelay's `eth` target and exposed via its public headers.
   - **Resolution:** Place the decompression utility in `evmrelay/include/eth/secp256k1_utility.hpp` + `evmrelay/src/eth/secp256k1_utility.cpp`. This follows existing patterns (all secp256k1 functions live there) and avoids link dependency questions. The `evmrelay` target already links `libsecp256k1::secp256k1`. SuperGenius code calls it through the evmrelay public header, not by direct libsecp256k1 linkage.

3. **Catch-up scan: can `eth_getLogs` accept OR'd topic0 values?** — RESOLVED
   - What we know: The current `make_get_logs_request` serializes each topic position as a single hex value (null or a Hash256). The Ethereum JSON-RPC spec supports arrays at topic positions for OR semantics (e.g., `"topics": [["hash1", "hash2"]]`), but the current C++ serialization code does not support this.
   - What's unclear: Whether to enhance `EventFilter` and `make_get_logs_request` to support topic OR arrays, or to simply make two separate `eth_getLogs` calls.
   - **Resolution:** Use two separate `eth_getLogs` calls for simplicity. The overhead is negligible (one extra RPC call per chain during startup, each ~100-500ms). Enhancing the serialization would touch evmrelay internals and require more testing. This matches the existing pattern of simplicity over optimization.

### Known Threat Patterns for secp256k1 Bridge Decompression

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Malformed X coordinate (not on curve) → nullopt | Denial of Service | `secp256k1_ec_pubkey_parse` returns 0 for invalid points; return nullopt, log warning, skip event |
| Point-at-infinity (X=0) injected as destination | Tampering | Validate X is non-zero before decompression; secp256k1 rejects infinity in compressed format |
| Timing side-channel on fixed-parity decompression | Information Disclosure | Single 0x02 prefix used deterministically (no parity loop); secp256k1 library itself is constant-time |
| Integer overflow in byte reversal (contract → big-endian) | Tampering | Use fixed-size `std::array<uint8_t, 32>`, loop bounded by `.size()`; no dynamic allocation |
| Resource exhaustion (repeated context creation in event flood) | Denial of Service | secp256k1 context creation/destruction is cheap (~microseconds). If event flood is a concern, batch-process or rate-limit at EthWatchService level (existing protection) |

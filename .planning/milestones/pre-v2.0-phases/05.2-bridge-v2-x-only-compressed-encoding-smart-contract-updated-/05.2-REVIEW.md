# Phase 05.2: Code Review Report

**Reviewed:** 2026-06-18T00:00:00Z
**Depth:** standard
**Files Reviewed:** 10
**Status:** issues_found

## Summary

Reviewed the Bridge V2 X-only compressed encoding implementation across the C++ account layer (`BridgeRelayer`, `GeniusNode` catch-up scan), the evmrelay event registry and `secp256k1_utility`, plus their unit tests.

The crypto core (`DecompressXOnlyPubkey`) is implemented carefully: correct libsecp256k1 prefix selection, correct context lifecycle (create/destroy per call — no leak), and correct on-curve failure handling (returns `nullopt`). The v1/v2 variant dispatch in `BridgeRelayer::OnWatchEvent` is sound and the `outcome::policy::all_narrow` UB traps are correctly guarded.

However, two BLOCKER-class defects exist in the `GeniusNode::PerformStartupCatchupScan` v1/v2 catch-up path: (1) historical burns are minted with `amount = 0` for every entry, and (2) the destination for v1 historical burns is left empty (and v2 inherits a hardcoded `dev_config_.TokenID` instead of the event's token id). Both result in **silent data loss / incorrect mint records** during startup catch-up — the most dangerous failure mode for a bridge because it produces transactions that look successful but carry wrong values. There is also a cross-cutting correctness assumption (bytes32 byte ordering between the Solidity contract and `DecompressXOnlyPubkey`) that is only validated by a circular self-consistency test, not against `GetAddress()` or a known on-chain vector.

Additional warnings cover exception-safety in the event-dispatch hot path, magic-number violations of the project's hard "no magic numbers" rule, and dead/placeholder test data.

## Critical Issues

### CR-01: Catch-up scan mints historical burns with `amount = 0`

**File:** `src/account/GeniusNode.cpp:2320-2325`
**Issue:** The `process_logs` lambda unconditionally calls `MintFunds` with a hardcoded `0` amount for every historical burn it discovers — for both the v1 (`BridgeSourceBurned`) and v2 (`BridgeOutInitiated`) queries. The inline comment even admits it: `// amount — derived from burn event data on full decode`, but the derivation is never performed. For v2 logs the surrounding code already fully decodes the 6 non-indexed params (including `amount` at decoded index 1) yet discards them. For v1 logs the `rpc_log.log.data` is never decoded at all.

Result: every historical burn backfilled during startup catch-up is recorded as a zero-value mint. This is silent data loss — the mint succeeds (returns a value), the burn is marked backfilled, and the log says "backfilled historical burn", but the user receives nothing. Worse, the dedup set (`seen_tx_hashes`) and the `IsOutPointConsumed` guard then prevent the same burn from being re-processed correctly later.

This is not a pre-existing v1 issue that can be deferred: the v2 path was newly written in this phase and reproduces the bug, and the phase explicitly expanded the catch-up scan to query both signatures.

**Fix:** Decode `amount` (and `token_id`) from the event data and pass the real values. For v2 the decode already happens — reuse it. Sketch:
```cpp
// inside process_logs, for both v1 and v2:
//   decode log.data per the relevant event signature, extract amount (uint256)
//   → convert via Uint256ToUint64 (same helper BridgeRelayer uses) → pass to MintFunds.
const uint64_t amount = /* decoded + overflow-checked */;
auto result = transaction_manager_->MintFunds(
    amount,
    tx_hash_hex,
    std::to_string( chain_entry.chain_id ),
    /* token_id from event, not dev_config_.TokenID */,
    destination );
```
For v1, the 6-param signature must be decoded (today it is skipped entirely and `destination` is left empty — see CR-02).

### CR-02: Catch-up scan leaves v1 `destination` empty and hardcodes `dev_config_.TokenID` for all burns

**File:** `src/account/GeniusNode.cpp:2247-2326`
**Issue:** In `process_logs`, when `is_v2 == false` the code never decodes `rpc_log.log.data`, leaving `destination` as an empty `std::string` and falling through to `MintFunds(... dev_config_.TokenID, destination)`. So every backfilled v1 burn is minted with a blank destination and the node's configured token id, regardless of what the event actually carried. For v2, the destination is correctly decompressed but the token id is *still* `dev_config_.TokenID` rather than the event's `id` (decoded index 0 of the v2 data). The live-watch path (`BridgeRelayer::OnWatchEvent`) correctly extracts both `token_id` (`TokenID::FromUint256(values[1])`) and the destination — so the catch-up scan and the live path produce **different mint records for the same logical event**.

Concretely for v2: the scan decodes `id`/`amount`/`sgnsDestination`/`destinationYOdd` and then throws away `id`, passing `dev_config_.TokenID`. If the bridge ever carries more than one token id, historical v2 burns get credited to the wrong token.

**Fix:** Decode the v1 log data (6 params: `id, amount, srcChainID, destChainID, sgnsDestination(bytes)`) and construct `destination` from the 64-byte `sgnsDestination` exactly as `BridgeRelayer::OnWatchEvent` does (`rlp::base::parse::hex_bytes(...)`). For both v1 and v2, pass `TokenID::FromUint256(decoded_id, Endianness::BIG)` instead of `dev_config_.TokenID`. The catch-up scan and the live path must agree on every field of the `MintFunds` call.

## Warnings

### WR-01: `DecompressXOnlyPubkey` byte-order assumption is only validated by a circular test

**File:** `evmrelay/src/eth/secp256k1_utility.cpp:175-251`, `evmrelay/test/eth/secp256k1_utility_test.cpp:182-267`
**Issue:** `DecompressXOnlyPubkey` reverses its 32-byte input before handing it to libsecp256k1, on the assumption that the bytes arrive in "contract byte order (LSB first in hex)" (per the docstring at `secp256k1_utility.hpp:33-34` and the phase context). But `eth::abi::decode_log_data` returns the `bytes32` word **verbatim** from the ABI stream (`abi_decoder.cpp:102-105`), i.e. standard big-endian/MSB-first EVM layout. Whether the produced key is correct therefore hinges entirely on the Solidity contract emitting the X coordinate in little-endian — a non-standard choice.

The unit tests (`DecompressEvenYKnownVector`, `DecompressOddYKnownVector`, `DecompressRoundTrip`) do **not** validate this against the production `GetAddress()` or against `secp256k1_address_from_private_key`. They build `expected_destination` using the exact same `to_contract_order` + `hex_bytes` transform the function under test applies, then assert equality — a tautology. If the contract actually emits big-endian (the universal secp256k1 convention), every v2 mint will be credited to the wrong destination and the tests will still pass.

**Fix:** Add at least one test that derives the full uncompressed key from a private key via `secp256k1_pubkey_create`, lays it out the way `GetAddress()` returns it, then asserts `DecompressXOnlyPubkey(<raw ABI bytes32>, parity) == GetAddress()`. Critically, the test must feed `DecompressXOnlyPubkey` the bytes in the same orientation the contract emits — i.e. exercise the real `decode_log_data` path on a synthetic log, not a hand-reversed array. Without this, the byte-order contract between Solidity and C++ is unverified.

### WR-02: `OnWatchEvent` uses throwing `std::get` on the variant without `noexcept` or try/catch

**File:** `src/account/BridgeRelayer.cpp:236-240, 266, 276, 283`
**Issue:** Project convention (CLAUDE.md) mandates noexcept-by-default, `outcome::result` for errors, and "no exceptions in hot paths." `OnWatchEvent` is invoked from the watch-service callback (line 133-144) on the watcher thread. It calls `std::get<intx::uint256>(notification.values[1..4])`, `std::get<Address>(...)`, `std::get<ByteBuffer>(...)`, `std::get<Hash256>(...)`, and `std::get<bool>(...)` without preceding `holds_alternative` checks on the common params. If the decoder ever yields a different alternative for an index (e.g. a registry change, a corrupted param list, or a future `kInt` widening), `std::get` throws `std::bad_variant_access`. The callback lambda does not catch it and `OnWatchEvent` is not `noexcept`, so the exception propagates into the watch service's dispatch loop. The v2 branch partially guards `values[5]`/`values[6]` with `holds_alternative`, but params 0-4 do not.

**Fix:** Either mark the function `noexcept` and replace every `std::get` with `std::get_if` + early-return on null, or wrap the body in a single `try/catch(const std::exception&)` that logs and returns. At minimum, add `holds_alternative` guards for `values[0..4]` mirroring the existing guards for `values[5]`/`values[6]`.

### WR-03: v1 request id and `to_block` are unnamed magic numbers

**File:** `src/account/GeniusNode.cpp:2353, 2395`
**Issue:** CLAUDE.md mandates `constexpr` `kCamelCase` named constants for *all* numeric literals ("NEVER use magic numbers ... This includes ... status codes, timeouts, array indices"). The v2 query was given a named constant (`kV2LogsRequestId = 2`, line 2394) and the block-number request a named constant (`kBlockNumberRequestId = 99`, line 2161), but the v1 get-logs call still uses a bare literal `1` (line 2353: `make_get_logs_request( filter, from_block, 0, 1 )`) and the `to_block` argument `0` (meaning "latest") is a bare literal in both the v1 (line 2353) and v2 (line 2395) calls. This is inconsistent within the same function and violates the project rule.

**Fix:**
```cpp
constexpr uint64_t kV1LogsRequestId  = 1;
constexpr uint64_t kLatestBlockTag    = 0; // eth_getLogs to_block = 0 means "latest"
auto v1_request = eth::rpc::make_get_logs_request( filter, from_block, kLatestBlockTag, kV1LogsRequestId );
auto v2_request = eth::rpc::make_get_logs_request( filter_v2, from_block, kLatestBlockTag, kV2LogsRequestId );
```

### WR-04: `EventRegistry` is not thread-safe and is accessed concurrently-ish at runtime

**File:** `evmrelay/include/eth/eth_watch_cli.hpp:52-78, 85-167`
**Issue:** `event_registry()` returns a reference to a function-local `static EventRegistry`. The static initialization is thread-safe (C++11), but the `unordered_map` itself has no internal synchronization. The docstring says registrations should happen "once at startup before creating any watchers" — but nothing enforces this, and `lookup`/`params_for` are `noexcept` non-const-qualified reads that race with any concurrent `register_event`. `BridgeRelayer::Start` calls `event_registry().params_for(...)` once per chain (lines 88, 96); if `Start` is ever invoked again while another component is mid-`register_event`, it's a data race on the map. Given the project's bridge components are observer-driven and can be re-triggered, this is a latent race.

**Fix:** Either (a) freeze the registry after first watcher creation (e.g. a `seal()` method that flips an `std::atomic<bool>` and makes `register_event` a no-op/error), or (b) guard the map with a `std::shared_mutex` (shared for `lookup`, exclusive for `register_event`). Option (a) is simpler and matches the documented usage contract.

### WR-05: `secp256k1_utility.cpp` `#include <secp256k1_recovery.h>` is correct but the file duplicates the context-per-call pattern 3x

**File:** `evmrelay/src/eth/secp256k1_utility.cpp:62-87, 89-131, 133-173, 175-251`
**Issue:** Every public function in this translation unit creates and destroys its own `secp256k1_context*` (4 separate create/destroy pairs). This is correct (no leak) and safe (no shared mutable state), but it pays the full context-allocation cost on every signature verify / recover / decompress call. For the hot path (`OnWatchEvent` → `DecompressXOnlyPubkey` per burn event, plus the catch-up scan which can fire dozens of decompressions in a tight loop), this is measurable. (Per scope rules this is flagged for the maintainability/robustness angle — repeated allocation is also a fragmentation risk on long-running nodes — rather than pure perf.)

**Fix:** Introduce a process-local `secp256k1_context*` (or `unique_ptr` with a custom deleter calling `secp256k1_context_destroy`) initialized once, marked `thread_local` if the library is not used cross-thread, or guarded by the existing context-clone API. At minimum, document the per-call cost so callers understand the catch-up scan's allocation profile.

### WR-06: `OnWatchEvent` mixes `outcome::result` and raw values; `result.value()` after `has_error()` is fine but the chain_id narrowing is unchecked

**File:** `src/account/BridgeRelayer.cpp:246-255`
**Issue:** Line 255: `const std::string chain_id = std::to_string( static_cast<uint64_t>( src_chain ) );` narrows `intx::uint256` → `uint64_t` with **no overflow check**, even though the very next block of code (lines 246-252) carefully overflow-checks `amount` via `Uint256ToUint64`. If `srcChainID` ever exceeds `uint64_t::max` (malicious or misconfigured contract), `static_cast<uint64_t>` silently truncates and `MintFunds` receives a wrong chain id. The same unchecked narrowing happens in `GeniusNode.cpp:2323` (`std::to_string( chain_entry.chain_id )`) but there `chain_id` is already `uint64_t` so it's safe; in `BridgeRelayer` it's `intx::uint256`.

**Fix:** Route `src_chain` through `Uint256ToUint64(src_chain, "srcChainID")` exactly like `amount`, and return early on failure.

### WR-07: `WriteTempChainsConfig` uses a fixed shared path — test collision risk

**File:** `test/src/startup/startup_wiring_test.cpp:52-59`
**Issue:** The helper writes to `fs::temp_directory_path() / "test_bridge_chains_config.json"` — a fixed filename, not unique. If the test binary is run in parallel (CI matrix, `ctest -jN`), or if a previous run crashed mid-test, the file is overwritten or left stale and the next test reads wrong contents. Several tests in this file (lines 203, 230, 274, 409, 435, 455, 526, 551) all share this single filename sequentially.

**Fix:** Use `fs::unique_path()` (Boost) or `std::tmpfile`/`mkstemp` to generate a per-call unique path, and pass the path explicitly to `Initialize` rather than relying on the working directory.

### WR-08: `BridgeRelayer::Stop()` is a documented no-op — watches are never unregistered

**File:** `src/account/BridgeRelayer.cpp:203-208`, `src/account/BridgeRelayer.hpp:58-61`
**Issue:** `Stop()` only logs. The class stores `chain_watches_` (the v1+v2 watch ids per chain, line 90) but never calls `watch_service_->unwatch(...)` (or whatever the API is). The header even says "currently a no-op — EthWatchService lifecycle is external." For the bridge, this means shutdown does not detach callbacks; if the `BridgeRelayer` is destroyed while the `EthWatchService` still holds the callback lambda (which captures `weak_from_this()`), the weak pointer expires and events are silently dropped — acceptable. But if the *same* `EthWatchService` is reused across node restart-without-shutdown (the relayer is re-created), the old watch ids accumulate and the old (expired-weak) callbacks run on every event, wasting work and polluting logs. The `chain_watches_` map is populated for exactly this cleanup purpose but is unused.

**Fix:** Implement `Stop()` to iterate `chain_watches_` and call the service's unwatch for both `.first` and `.second` (guarding for the "one version failed to register" case where the id may be 0). At minimum, if unregistration is genuinely unnecessary, delete `chain_watches_` after `Start` to avoid implying cleanup that never happens.

### IN-02: `parse_address` in `eth_watch_cli.hpp` ignores parse failure detail

**File:** `evmrelay/include/eth/eth_watch_cli.hpp:28-33`

Minor, but the surrounding tests (`ParseAddressTooShort`, `ParseAddressInvalidChar`, etc.) already imply these cases are meaningful.

The project style (CLAUDE.md) mandates PascalCase for methods but test names typically follow the prevailing file convention. Minor inconsistency.

### IN-04: `eth_watch_cli.hpp` event-registry comments duplicate the signature string in code and comment

**File:** `evmrelay/include/eth/eth_watch_cli.hpp:136-162`
**Issue:** The v1 and v2 bridge event registrations repeat the full event signature twice (once in the comment `event BridgeSourceBurned(...)`, once in the `register_event("BridgeSourceBurned(...)", {...})` string literal). If the signature is ever edited in one place but not the other, the comment drifts silently. Not a bug, but a maintainability nit given how load-bearing these strings are (they're the topic0 seed).

**Fix:** Optional — define the signatures as `inline constexpr std::string_view kBridgeSourceBurnedSig = "...";` and reference them from both the comment-doxygen and the registration call.

### IN-05: `process_logs` lambda captures `[&]` and is ~150 lines — high cyclomatic complexity

**File:** `src/account/GeniusNode.cpp:2202-2350`
**Issue:** The `process_logs` lambda inside `PerformStartupCatchupScan` is roughly 150 lines with 5 distinct early-return paths, a nested v2 decode block, and a try/catch. This exceeds the project's function-size guidance and makes the v1/v2 behavioral difference hard to audit (which is exactly how CR-01/CR-02 went unnoticed). Combined with the `[&]` capture of 4 outer variables, it's a readability and testability smell.

**Fix:** Extract `process_logs` into a private member function `ProcessCatchupLogBatch(const std::vector<RpcLog>&, bool is_v2, ChainEntry, std::set<std::string>& seen, size_t& backfilled, size_t& skipped)`, which also makes it directly unit-testable (today the entire scan is untested except via structural mocks).

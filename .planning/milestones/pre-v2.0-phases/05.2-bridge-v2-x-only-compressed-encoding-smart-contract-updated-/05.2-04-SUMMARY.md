# Phase 05.2 Plan 04: Bridge V2 Integration Tests Summary

Added integration test coverage for the v1+v2 bridge coexistence built in Plans 01-03: 4 EventRegistry tests verifying `BridgeOutInitiated` is registered with `kBytes32` param 5 and `kBool` param 6 (and v1 retained), 3 BridgeRelayer tests verifying v2 `Hash256` variant dispatch reaches decompression + the null-TerminalManager log without `bad_variant_access` plus v1 regression safety, and 3 catch-up scan tests verifying the v2 topic0 hash is deterministic, differs from v1, and is non-zero. Also fixed the `BridgeRelayerTestAccess::ChainWatches()` accessor for Plan 02's new `pair<EventWatchId, EventWatchId>` map type — this was a build blocker (`bridge_relayer_test` did not compile against the Plan 02 changes).

## What Was Built

### Task 1 — EventRegistry v2 verification (commit 00bf612, evmrelay submodule)
Added 4 `EventRegistryTest` cases to `evmrelay/test/eth/eth_watch_cli_test.cpp`:
- `RegistryContainsBridgeOutInitiated` — `lookup` returns non-null with 7 params.
- `BridgeOutInitiatedParam5IsBytes32` — param 5 is `kBytes32`, not `kBytes`, not indexed.
- `BridgeOutInitiatedParam6IsBool` — param 6 is `kBool`, not indexed, named `destinationYOdd`.
- `BridgeSourceBurnedStillRegistered` — v1 event retained with 6 params, param 5 is `kBytes` (D-05).

Full suite: 21/21 pass (17 pre-existing + 4 new).

### Task 2 — BridgeRelayer v2 dispatch + dual-watch tests (commit d57d9f05, parent repo)
Three changes to `test/src/account/bridge_relayer_test.cpp`:
1. **Build-blocker fix:** Updated `ChainWatches()` accessor return type to `const std::unordered_map<std::string, std::pair<eth::EventWatchId, eth::EventWatchId>>&` to match Plan 02's `chain_watches_` member type. Without this, `bridge_relayer_test` did not compile.
2. **Updated existing assertions:** `MultiChainStart` and `OnRpcEndpointsReadyDelegatesToStart` now assert both `.first` (v1) and `.second` (v2) watch ids are non-zero.
3. **Added v2 infrastructure + tests:** `MakeV2BurnNotification` helper (pushes `Hash256` at `values[5]`, `bool` Y-parity at `values[6]`), plus three tests:
   - `OnWatchEventDispatchesV2Event` — v2 notification with a valid on-curve X-only key (canonical secp256k1 private-key-1 vector) dispatches through the `Hash256` branch, decompresses, and reaches the null-TM log without throwing.
   - `OnWatchEventV1StillWorks` — v1 `ByteBuffer` path regression.
   - `DecompressMatchesKnownVector` — REQ-V2-05 integration: `DecompressXOnlyPubkey` on the canonical vector yields a 128-char destination whose X half matches the input.

Full suite: 22/22 pass (19 pre-existing + 3 new).

### Task 3 — v2 catch-up scan topic0 tests (commit 4e668848, parent repo)
Added `kBridgeEventSignatureV2` constant and 3 `StartupWiringTest` cases to `test/src/startup/startup_wiring_test.cpp`:
- `BridgeOutInitiatedTopic0IsDeterministic` — same signature → same hash, non-zero.
- `V1andV2Topic0Differ` — v1 and v2 topic0 hashes differ (no dedup collision, D-12).
- `V2Topic0IsNonZero` — v2 hash is 32 bytes and non-zero.

Full suite: 24/24 pass (21 pre-existing + 3 new).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Fixed ChainWatches() accessor for Plan 02's pair map type (build blocker)**
- **Found during:** Task 2 Step 1
- **Issue:** Plan 02 changed `BridgeRelayer::chain_watches_` from `unordered_map<string, EventWatchId>` to `unordered_map<string, pair<EventWatchId, EventWatchId>>`, but the existing `BridgeRelayerTestAccess::ChainWatches()` accessor in `bridge_relayer_test.cpp` still returned the old type, so `bridge_relayer_test` did not compile. This was called out as a known build blocker in the execution context.
- **Fix:** Updated the accessor return type to the pair map. Also updated two existing tests (`MultiChainStart`, `OnRpcEndpointsReadyDelegatesToStart`) that compared `it->second` against `0` — a pair-vs-int comparison that would not compile — to instead check both `.first` and `.second` are non-zero.
- **Files modified:** `test/src/account/bridge_relayer_test.cpp`
- **Commit:** d57d9f05

**2. [Rule 1 - Bug] Two existing tests compared the map value (now a pair) against 0**
- **Found during:** Task 2 Step 1 (consequence of the accessor fix)
- **Issue:** `MultiChainStart` (line ~370) and `OnRpcEndpointsReadyDelegatesToStart` (line ~525) asserted `EXPECT_NE( it->second, 0 )`. After the accessor type change, `it->second` is a `std::pair`, which has no built-in inequality comparison against `int 0`.
- **Fix:** Changed both to `EXPECT_NE( it->second.first, 0 )` + `EXPECT_NE( it->second.second, 0 )`, asserting both v1 and v2 watch ids are registered and non-zero (matching Plan 02's D-21 dual-registration contract).
- **Files modified:** `test/src/account/bridge_relayer_test.cpp`
- **Commit:** d57d9f05

**3. [Rule 3 - Blocking] eth_watch_cli_test builds only in the evmrelay submodule build dir**
- **Found during:** Task 1 verification
- **Issue:** The plan's `<verify>` snippet referenced `cd evmrelay/build/OSX/Debug` for `eth_watch_cli_test`. Verification confirmed `eth_watch_cli_test` is NOT a target in the top-level `build/OSX/Debug` (only `bridge_relayer_test` and `startup_wiring_test` are). The top-level build links `libevmrelay.a` but does not expose the evmrelay test binaries. Task 1's commit therefore lands in the evmrelay submodule (`develop` branch) and the parent repo's submodule pointer is advanced in the final docs commit.
- **Fix:** Built and ran `eth_watch_cli_test` from `evmrelay/build/OSX/Debug`; staged the submodule pointer bump (`5c755c7` → `00bf612`) in the parent repo's final commit so the Task 1 test is recorded.
- **Commit:** submodule 00bf612; parent pointer advanced in final docs commit.

**4. [Adaptation] Used 2-arg DecompressXOnlyPubkey(x, destination_y_odd), not the 1-arg signature sketched in the plan's <interfaces>**
- **Found during:** Task 2 pre-implementation interface check
- **Issue:** This plan's `<interfaces>` block sketched `DecompressXOnlyPubkey(const std::array<uint8_t,32>&)` (1 arg). Plan 01 actually delivered the 2-arg `DecompressXOnlyPubkey(contract_x_bytes, destination_y_odd)`. This matches what Plans 02 and 03 already documented.
- **Fix:** Called the 2-arg form with `destination_y_odd=false` (even-Y canonical vector). No functional divergence from the plan's intent.

# Phase 05.2: Bridge V2 — X-only Compressed Encoding - Context

**Gathered:** 2026-06-18
**Status:** Ready for planning
**Source:** ROADMAP.md + codebase analysis (evmrelay, BridgeRelayer, GeniusAccount, secp256k1 utilities)

<domain>
## Phase Boundary

Upgrade the bridge smart contract and C++ watcher to use X-only compressed (32-byte) SuperGenius public keys instead of full 64-byte uncompressed keys. The contract changes from `BridgeSourceBurned` (with `bytes sgnsDestination`) to `BridgeOutInitiated` (with `bytes32 sgnsDestination, bool destinationYOdd`). The `bool destinationYOdd` signals the Y parity (false=even/0x02, true=odd/0x03), eliminating the Y-parity ambiguity. The C++ side uses this parity to decompress the X-only key to full X+Y matching `GetAddress()`. The catch-up scan must handle both v1 and v2 event topic0 hashes.

This is an urgently-needed optimization — storing 64 bytes of public key per bridge event is wasteful when 32 bytes (X-only) suffices.
</domain>

<decisions>
## Implementation Decisions

### Smart Contract Changes (external — already specified in ROADMAP)
- **D-01:** New function signature: `bridgeOut(uint256 amount, uint256 id, uint256 destChainID, bytes32 sgnsDestination, bool destinationYOdd)`. Replaces the old `bridgeOut` that accepted an Ethereum address. The `sgnsDestination` is a 32-byte X-only compressed secp256k1 public key (pure X coordinate). The `destinationYOdd` flag (false=even/0x02, true=odd/0x03) explicitly signals the Y parity, eliminating ambiguity.
- **D-02:** New event: `BridgeOutInitiated(address indexed sender, uint256 id, uint256 amount, uint256 srcChainID, uint256 destChainID, bytes32 sgnsDestination, bool destinationYOdd)`. Replaces `BridgeSourceBurned(address,uint256,uint256,uint256,uint256,bytes)`. The 6th parameter changed from `bytes` (dynamic) to `bytes32` (fixed 32 bytes). A 7th parameter `bool destinationYOdd` was added for explicit Y parity signaling.
- **D-03:** The old `BridgeSourceBurned` event is retired. No backward-compatible dual-emit needed — the new contract replaces the old deployment.

### C++ Watcher: Event Registry
- **D-04:** Register the new `BridgeOutInitiated(address,uint256,uint256,uint256,uint256,bytes32,bool)` event signature in `eth::cli::event_registry()` (in `evmrelay/include/eth/eth_watch_cli.hpp`). The 6th param type changes from `AbiParamKind::kBytes` (dynamic) to `AbiParamKind::kBytes32` (fixed 32 bytes). A 7th param `{AbiParamKind::kBool, false, "destinationYOdd"}` is added. The ABI decoding path already handles `bytes32` as Hash256 and `bool` as a value type.
- **D-05:** Keep the old `BridgeSourceBurned` registration in the registry for backward-compatible catch-up scanning — v1 burns already on-chain must still be processed.

### C++ Watcher: BridgeRelayer OnWatchEvent
- **D-06:** `BridgeRelayer::OnWatchEvent()` (in `src/account/BridgeRelayer.cpp`) currently decodes 6 params from `BridgeSourceBurned`. It must be updated to handle the new `BridgeOutInitiated` event format with 7 params: `values[5]` is a `bytes32` (32-byte X-only key) and `values[6]` is a `bool` (destinationYOdd). The v1 format had `values[5]` as `bytes` (dynamic ByteBuffer).
- **D-07:** After extracting the 32-byte X-only key and the `bool destinationYOdd` from the event, decompress to a full 64-byte X+Y public key. The parity is explicit: `destinationYOdd ? 0x03 : 0x02` selects the correct secp256k1 compressed key prefix. Parse via `secp256k1_ec_pubkey_parse`, serialize uncompressed, extract X (bytes 1..32) and Y (bytes 33..64) skipping the 0x04 prefix byte.

### Key Decompression: X-only → Full X+Y
- **D-08:** SuperGenius `GetAddress()` returns the full 64-byte X+Y concatenated public key hex (128 chars). The V1 bridge received this directly. V2 receives only the 32-byte X. The decompression must produce the EXACT same X+Y as the account's `GetAddress()`.
- **D-09 (LOCKED — explicit parity via bool):** The `BitcoinKeyGenerator` (in `ProofSystem/include/ProofSystem/BitcoinKeyGenerator.hpp`) already handles X-only compressed keys with a parity prefix byte (`02` for even Y, `03` for odd Y). The bridge receives pure X plus an explicit `bool destinationYOdd` in the event. Decompression uses the parity directly:
  - `uint8_t prefix = destinationYOdd ? 0x03 : 0x02;` — deterministic, no trial needed.
  - Prepend prefix to X, call `secp256k1_ec_pubkey_parse()`, serialize uncompressed.
  - Extract the 64-byte raw public key from `uncompressed[1..64]` (skipping 0x04 prefix).
  - If the X+parity combination is not on the curve, the event data is malformed and decompression returns nullopt.
- **D-10:** The decompression should be implemented as a free function (per project API design principles): `std::optional<std::string> DecompressXOnlyPubkey(const std::array<uint8_t, 32>& contract_x_bytes, bool destination_y_odd) noexcept -> std::optional<std::string>` returning the 128-char hex destination (X+Y concatenated), or nullopt if decompression fails (invalid X+parity combination not on curve).

### Versioned Catch-Up Scan
- **D-11:** `GeniusNode::PerformStartupCatchupScan()` (in `src/account/GeniusNode.cpp`) currently computes topic0 from `BridgeSourceBurned(address,uint256,uint256,uint256,uint256,bytes)`. It must also query logs for the new `BridgeOutInitiated` topic0 to catch v2 burns.
- **D-12:** The catch-up scan should query BOTH topic0 hashes (v1 and v2) in a single `eth_getLogs` call using the topics array OR operator (topic0=[hash1, hash2]). This avoids doubling the RPC call count.
- **D-13:** For each v2 log found, the scan must decompress the X-only key (D-08) before calling `MintFunds()`.

### BridgeRelayer: Per-Chain Watch Registration
- **D-14:** `BridgeRelayer::Start()` (in `src/account/BridgeRelayer.cpp`) registers a single watch per chain for the `BridgeSourceBurned` event. It must now register TWO watches per chain: one for `BridgeSourceBurned` (v1 — backward compat for existing deployments until they're upgraded) and one for `BridgeOutInitiated` (v2). Or, the contract address in `bridge_chains_config.json` determines which event to watch (v1 contract = old event, v2 contract = new event).
- **D-15:** Simplest approach: register both events for every chain. The watch for the wrong version will simply never fire (the contract doesn't emit it). This avoids config complexity. Best-effort per D-21 from Phase 5.

### Claude's Discretion
- Exact secp256k1 decompression implementation (which library/approach)
- Whether to use `std::array<uint8_t, 32>` or `std::vector<uint8_t>` for the X-only key
- File location for the decompression utility (suggested: `src/account/` or `evmrelay/include/eth/`)
- Whether to also update `BridgeRpcWatcher` in `src/watcher/` if it independently processes bridge events
- Log level and error handling for unrecognized event signatures in `OnWatchEvent`
- Whether to add a unit test for secp256k1 decompression against known test vectors
</decisions>

<specifics>
## Specific Ideas

- **Decompression approach:** Use libsecp256k1's `secp256k1_ec_pubkey_parse()` for decompression (not hand-rolled modular sqrt). Build a 33-byte compressed key: `[prefix][X_bigendian]` where `prefix = destinationYOdd ? 0x03 : 0x02`. Parse → serialize uncompressed → extract `uncompressed[1..64]` (skip 0x04 prefix) as the 64-byte raw public key. Reverse byte ordering to match contract format. The `EthereumKeyGenerator::BuildPublicKey()` shows the expected byte ordering: X is the last half, Y is the first half of the 128-char hex string.
- **Parity (explicit via bool):** The contract event includes `bool destinationYOdd` — `false` = even Y (0x02 prefix), `true` = odd Y (0x03 prefix). The C++ decompression uses this directly: `uint8_t prefix = destinationYOdd ? 0x03 : 0x02;`. No convention enforcement needed — the event data carries the ground truth. The `uncompressed[1..64]` bytes (skipping the 0x04 prefix) form the 64-byte raw public key.
- **`bytes32` and `bool` ABI types:** In `eth::abi::AbiParamKind`, `kBytes32` maps to `codec::Hash256 = std::array<uint8_t, 32>`. The Solidity `bool` type maps to `kBool` (already in the enum). The `bool destinationYOdd` at param index 6 will be decoded as a boolean value in the ABI data. Both types are fixed-size (not dynamic like `bytes`).
- **Event topic0:** The Keccak-256 hash of `BridgeOutInitiated(address,uint256,uint256,uint256,uint256,bytes32,bool)` is the new topic0. The old topic0 is `keccak256("BridgeSourceBurned(address,uint256,uint256,uint256,uint256,bytes)")`. Both must be computed and used in the catch-up scan OR query.
- **Backward-compatible watch:** During the transition period, both `BridgeSourceBurned` and `BridgeOutInitiated` watches should be registered per chain. Once all deployed contracts are upgraded to v2, the v1 watch can be removed. The simplest approach: register both unconditionally. The unfired watch is harmless.
- **Test vectors:** Use known secp256k1 test vectors (e.g., secp256k1 generator point) with both even-Y (0x02) and odd-Y (0x03) compressed representations. A test should: take a known 32-byte X + bool parity → decompress → verify the resulting 64-byte raw key matches the known uncompressed public key → verify destination matches expected `GetAddress()` output.
</specifics>

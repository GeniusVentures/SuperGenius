# Phase 05.1: Refactor — Move RPC Endpoint Initialization from GeniusNode to ChainRpcEndpointProvider - Context

**Gathered:** 2026-06-16
**Status:** Ready for planning

<domain>
## Phase Boundary

Move `GeniusNode::InitializeRpcEndpoints()` (~175 lines of path resolution, JSON parsing, `ChainRpcEndpointProvider` construction, `Initialize()` call, and `IInputValidator::Register()`) into `ChainRpcEndpointProvider::Initialize()`. GeniusNode becomes a thin orchestrator: resolve the config path, construct the provider, register observers, and post `Initialize()` to the io_context. BridgeRelayer receives the chain/contract list via an observer callback, eliminating GeniusNode as the middleman for chain data handoff.

This refactor does NOT change the startup sequence (InitRpcEndpoints → BridgeRelayer::Start ordering from Phase 5 D-04), the `bridge_chains_config.json` schema (adds only a `chain_id` field), or the async non-blocking nature of the initialization.
</domain>

<decisions>
## Implementation Decisions

### What Moves and What Stays
- **D-01:** `ChainRpcEndpointProvider::Initialize()` accepts a `std::filesystem::path` to `bridge_chains_config.json`. Path resolution (BaseWritePath → binary-relative → CWD fallback) stays in GeniusNode — it knows `DevConfig::BaseWritePath` and the binary location. JSON reading, parsing, ChainRpcProviderConfig construction, and endpoint wiring all move into the provider.
- **D-02:** `IInputValidator::Register()` moves into `ChainRpcEndpointProvider::Initialize()` as the final step after wiring endpoints. Only the `provider.Initialize(path, validator, logger)` call remains in GeniusNode. The `bridge_chains_` member is removed from GeniusNode.

### Coupling Pattern — Observer
- **D-03:** Observer callback pattern for BridgeRelayer ↔ ChainRpcEndpointProvider coupling:
  - `ChainRpcEndpointProvider` defines `IBridgeInitObserver` interface with a single method: `OnRpcEndpointsReady(std::vector<ChainContractPair> chains)`
  - `BridgeRelayer` implements `IBridgeInitObserver`. Its `OnRpcEndpointsReady()` calls `Start(chains)`.
  - Subscription is synchronous during GeniusNode construction/state transition: `provider.AddObserver(*bridge_relayer_)` before `boost::asio::post(provider.Initialize(...))`.
  - `Initialize()` notifies all observers at completion. Ordering is guaranteed: subscribe (sync) → post → Initialize (async) → callbacks (async, inside Initialize).
  - GeniusNode is no longer the middleman handing chain data from provider to BridgeRelayer.

### Chain ID Source
- **D-04:** The `kChainNameToId` static map (8 hardcoded entries in GeniusNode.cpp:2034-2043) is eliminated. Chain IDs are sourced from a new `chain_id` field in `bridge_chains_config.json` per chain entry. If a chain entry lacks `chain_id`, it is skipped with a warning.

### Claude's Discretion
- Exact `IBridgeInitObserver` declaration location (new header in `src/account/` vs. inline in `ChainRpcEndpointProvider.hpp`)
- Observer container type (`std::vector<IBridgeInitObserver*>` vs. `std::vector<std::reference_wrapper<IBridgeInitObserver>>`)
- Whether `BridgeRelayer` implements the observer directly or via a thin adapter
- `bridge_chains_config.json` schema documentation updates
- GeniusNode member variable changes (new `rpc_endpoint_provider_` unique_ptr, removal of `bridge_chains_`)
- Thread safety of observer list (single-threaded io_context usage is sufficient per existing patterns)

</decisions>

### Reusable Assets
- `ChainRpcEndpointProvider` — Already encapsulates ChainList loading, endpoint grouping by chain ID, and `SetRpcEndpoints()` wiring. Extend with JSON file reading and observer management.
- `BridgeRelayer` — Already has `Start(vector<ChainContractPair>)`. Add `IBridgeInitObserver` implementation.

- Allman/Ullman bracing, Doxygen headers, `constexpr` named constants

### Integration Points
- `GeniusNode` state machine — Provider construction + observer registration + `Initialize()` post happens during `INITIALIZING_TRANSACTIONS` (same place as current `InitializeAndStartBridge()`)
- `ChainRpcEndpointProvider::Initialize()` — Signature changes from `(validator, config, logger)` to `(path, validator, logger)`
- `BridgeRelayer` — Gains `IBridgeInitObserver` implementation
- `bridge_chains_config.json` — Gains optional `chain_id` field per chain entry

</code_context>

<specifics>
## Specific Ideas

- The observer list should use `IBridgeInitObserver*` (non-owning). GeniusNode owns both the provider and the BridgeRelayer — no lifetime issues.
- `Initialize()` should still return `bool` (true when at least one chain received endpoints), but the chain list itself goes to observers.
- `IInputValidator::Register()` call should happen per-chain inside the provider's `Initialize()` after `SetRpcEndpoints()`, replacing the loop currently at GeniusNode.cpp:2141-2144.
- The `bridge_chains_config.json` `chain_id` field should be a numeric value (not hex string) for consistency with evmrelay conventions.
</specifics>

<objective>
This plan delivers certificate-fallback deserialization in `OnConsensusCertificate` — when a standalone validator receives a certificate for a transaction it never saw (no CRDT sync), it deserializes the transaction from the certificate's embedded `NonceSubject.transaction_data` and runs it through `ChangeTransactionState(tx, CONFIRMED)`, which populates `tx_processed_m`, `utxo_outpoints_`, and `confirmed_nonces_`. This enables the existing `HasConfirmedInputConflict`, `VerifyParameters`, and `CheckTransactionReplayProtection` to detect double-spends and nonce replays from previously certified transactions — no new validation logic, no separate indexes.

Purpose: Close the double-spend and nonce-replay detection gap for standalone validators that lack CRDT transaction state (CONFLICT-01, NONCE-01). The fix is additive and localized — the existing validation infrastructure works automatically once the certificate path feeds it state.

Output: Modified `OnConsensusCertificate` with certificate-fallback deserialization block; test file with happy-path, edge-case, and regression test cases.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ConsensusCertificate → OnConsensusCertificate | Certificate data arrives via CRDT gossip (trusted consensus output). The certificate.proposal().subject().transaction_data is consensus-validated but may be from any Phase 1 peer. |
| embedded tx_data → DeSerializeTransaction | Protobuf bytes from certificate pass through deserialization. Malformed data from a buggy or malicious Phase 1 peer could trigger unexpected behavior. |
| deserialized tx → ChangeTransactionState(CONFIRMED) | Transaction object from certificate-embedded data enters the local state machine. Cross-account UTXO interaction is a potential concern (see Open Question #1 in RESEARCH.md). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Denial of Service | DeSerializeTransaction from certificate tx_data | mitigate | Defensive blake2b_256 hash check before deserialization; DeSerializeTransaction uses bounded protobuf ParseFromArray — already DoS-hardened from Phase 1 SANTZ-01. Malformed data returns Check::Approve (not crash/reject). |
| T-02-02 | Tampering | Certificate-embedded tx_data mismatch with tx_hash | mitigate | Hash integrity gate: computed_hash.toReadableString() compared against tx_hash parameter. Mismatch → log error + return Check::Approve (don't process wrong data, don't reject valid certificate). |
| T-02-03 | Repudiation | Replay of old certificates (re-processing) | accept | GetCertificateBySubjectHash + CheckCertificateForSubject at ConsensusManager level prevents duplicate certificate processing. ChangeTransactionState(CONFIRMED) guards against double-CONFIRMED (line 4905-4913). Already handled — no Phase 2 changes needed. |
| T-02-04 | Tampering | UTXO state poisoning via cross-account certificate processing | accept | Flagged as Open Question #1 in RESEARCH.md. If ParseTransaction incorrectly adds UTXOs for cross-account transactions, validator balance could be inflated. Mitigation deferred — requires testnet verification. If confirmed, add account-scoping guard in follow-up. Existing behavior already occurs when CRDT-synced txs enter non-owning nodes; not a new risk. |
| T-02-05 | Spoofing | Nonce state poisoning via certificate from different account | accept | SetPeerConfirmedNonce uses address field (tx source address) — stored per-address in confirmed_nonces_. Cross-account certificates populate the source account's nonce entry, not the local account's. Safe for standalone validator's own nonce chain. |

## Security Design Note

All certificate fallback failures return `Check::Approve`, never `Check::Reject`. Rationale: a ConsensusCertificate represents a consensus decision that has already been validated by the network. Rejecting it because the local node can't parse the embedded transaction data would cause a consensus fork. The conservative choice is to accept the certificate (honoring the network consensus) and log the local parsing limitation for operator investigation.

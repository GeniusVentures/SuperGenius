## Ordering constraints (code-verified)

- ProcessingNode::New (processing_node.cpp:10-51) calls Initialize (queue channel constructed,
  then processingQueueChannel->Listen(msSubscriptionWaitingDuration) at :204 with the 2000ms
  default from processing_node.hpp:59) and then AttachTo (:211-233), whose
  m_subTaskQueueAccessor->CreateResultsChannel + ConnectToSubTaskQueue subscribe the results
  channel. Both run INSIDE New, before the service can touch the node.
- The two node-creation sites apply the filter only AFTER New returns:
  AcceptProcessingChannel (processing_service.cpp:430-438) and HandleNodeCreationTimeout
  (:811-819). The grid channel is NOT affected (GeniusNode StartProcessing installs before
  Listen, :3557-3572).
- GlobalDB startup: INITIALIZING_DATABASE (GeniusNode.cpp:749-758) runs InitDatabase() (GlobalDB::New
  over pubsub_ + tx_globaldb_->Start(), :2106-2126), then account_->ConfigureDatabaseDependencies,
  then tx_globaldb_->AddListenTopic(ScopedProcessingChannel()) — the first live subscription. The
  registry-backed filter installs much later at INITIALIZING_TRANSACTIONS (:1121-1127) after
  NetworkRegistry::New (:1090-1098). Quorum/blockchain topics are added from
  INITIALIZING_BLOCKCHAIN (:852).
- No circular dependency blocks the interim install: the bootstrap membership
  (network_bootstrap_peers_) is plain config known at InitNetwork time; a lightweight
  config-backed predicate needs neither the registry nor the DB. NetworkRegistry stores the same
  strings verbatim as cached_network_peers_ (NetworkRegistry.cpp:289-299) and membership matching
  is base58 string comparison against PeerId::toBase58() (NetworkMembershipFilter.hpp:84-86) —
  the interim predicate mirrors exactly that.
- After 15-14, the broadcaster/channels also carry signing keys; the interim filter composes
  unchanged with the CR-G01 authentication (same OnMessage code path — verify sealed sends still
  pass under the interim filter in the new scenes).

**Reviewed:** 2026-07-13

## Summary

Fresh deep review of the 15 files in Phase 04.1 scope, covering the `creation_block`
plumbing, `find_contract_creation_blocks.py` rewrite, Plan 01 creation_block injection,
the `BridgeCatchupWatcher` forward-chunked scan, the `RpcHttpTransport` retry/backoff
layer, and both Anvil E2E test fixtures.

The review traced cross-file call chains: `ChainRpcEndpointProvider::Initialize` parses
`creation_block` from JSON -> `ChainContractPair` carries it -> `OnRpcEndpointsReady`
stores it in `catchup_chains_` -> `BridgeCatchupWatcher::poll_once` uses it as a
forward-scan floor. The `find_contract_creation_blocks.py` script downloads the
GeniusDiamond manifest, cross-references facet addresses, and binary-searches
`eth_getCode` to populate `creation_block` values.

The review surfaced **2 Critical** defects, both in `BridgeCatchupWatcher::poll_once`:
the per-chain `last_block_per_chain_` cursor is unconditionally advanced to
`current_block + 1` even when the scan was capped by `max_chunks` or when RPC calls
failed, permanently skipping unscanned blocks and silently losing burns. **8 Warnings**
cover test assertions that are trivially true (providing no real coverage), missing
RPC-URL validation in `FundAccount0WithGnus`, IPv6 parse failure in `split_host_port`,
silent CA-load failures, and dead code in the Python script. **5 Info** items address
minor robustness and style concerns.

## Critical Issues

### CR-01: poll_once advances last_block_per_chain_ past unscanned blocks when max_chunks caps the scan

**File:** `src/watcher/impl/bridge_catchup_watcher.cpp:371`
**Issue:** After the forward-chunked scan loop (lines 283-366), `last_block_per_chain_`
is unconditionally set to `to_block + 1` (which equals `current_block + 1`), regardless
of whether the loop actually scanned all the way to `to_block`. When `config_.max_chunks`
is non-zero and the scan is capped before reaching `current_block`, the cursor jumps past
all unscanned blocks. On the next poll, `from_block` = `current_block + 1` (from
`last_block_per_chain_`), so the unscanned range `[last_scanned_chunk_to + 1,
current_block]` is never revisited. Any burns in that range are permanently lost.

This is the production path: `GeniusNode::InitializeAndStartBridge` constructs the watcher
with `max_chunks = 0` (unlimited), so production scans ARE NOT affected. But the
`Config::max_chunks` field exists for a reason (rate-limit backpressure, test injection),
and any future production use of a non-zero `max_chunks` would silently drop burns.

The test `TwoPhaseScanBridgesGap` (Test C) uses `max_chunks = 3` on Phase 1, and Phase 1's
`last_block_per_chain_` is set to `current_block + 1` even though only 3 chunks (3000
blocks) were scanned. Phase 2 picks up from `fork - 5`, masking the gap in the test, but
the cursor advancement is still incorrect.

**Fix:**
```cpp
// After the scan loop, only advance the cursor to the last successfully scanned block.
{
    std::lock_guard lock( mutex_ );
    // If the loop completed (from_block > to_block), advance to to_block + 1.
    // If the loop was capped (chunks_done == max_chunks && from_block <= to_block),
    // advance only to the last scanned chunk_to + 1 so unscanned blocks are retried.
    if ( from_block > to_block )
    {
        last_block_per_chain_[chain_entry.chain_id] = to_block + 1;
    }
    else
    {
        // from_block was already advanced to chunk_to + 1 in the loop.
        // Use it as the next scan start — do NOT skip to current_block + 1.
        last_block_per_chain_[chain_entry.chain_id] = from_block;
    }
}
```

### CR-02: poll_once advances from_block and last_block_per_chain_ when RPC calls fail, silently dropping burns in failed chunks

**File:** `src/watcher/impl/bridge_catchup_watcher.cpp:356-371`
**Issue:** When a chunk's RPC call fails (`!v1_response.has_value()` and v2 also fails or
is absent), `chunk_ok` stays false, but `from_block` is still advanced to `chunk_to + 1`
(line 364) and the loop continues to the next chunk. At the end, `last_block_per_chain_`
is set to `to_block + 1` (line 371), so the failed chunk is never retried on the next poll.

If an RPC endpoint has a transient failure (timeout, 5xx, network blip) during a chunk
that contains burn events, those burns are silently lost — the watcher advances past them
and never queries that block range again. This violates the catch-up scan's core contract:
every historical burn must be discovered and minted.

The `chunk_ok` flag is computed but only used for a debug log message (line 356-362); it
does not gate cursor advancement.

**Fix:**
```cpp
// Do not advance from_block when the chunk failed — retry it on the next poll.
if ( !chunk_ok )
{
    logger->warn( "CatchUpScan: chunk {}-{} for chain {} failed — will retry on next poll",
                  from_block,
                  chunk_to,
                  chain_entry.chain_name );
    // Do NOT advance from_block; break out of the loop so the cursor stays
    // at the failed chunk's start.
    break;
}

from_block = chunk_to + 1;
++chunks_done;
```

And in the cursor update:
```cpp
{
    std::lock_guard lock( mutex_ );
    // Only advance to to_block + 1 if the scan completed without failures.
    // If we broke out early (RPC failure), from_block points at the failed chunk.
    last_block_per_chain_[chain_entry.chain_id] = from_block;
}
```

## Warnings

### WR-01: Test A assertion (balance >= initial_balance) is trivially true — provides zero coverage

**File:** `test/src/bridge_e2e/bridge_anvil_catchup_e2e_test.cpp:509-513`
**Issue:** `FullScanFromGenesisNoErrors` waits for
`node_main->GetBalance(dest_addr) >= initial_balance`. A balance can only stay the same
or increase from a catch-up scan (the scan only mints, never burns). This condition is
true at the very first poll (10ms into the wait), so `EXPECT_WAIT_FOR_CONDITION` succeeds
immediately without verifying that any burns were actually discovered or minted. The test
name claims to verify the scan "COMPLETES without error," but the assertion doesn't test
scan completion — it tests a tautology.

**Fix:** Assert that the balance increased by at least `kNumCatchupBurns * kMintAmount`
(the pre-node burns seeded in `SetUpTestSuite`), or assert that
`GetLastProcessedBlock` advanced past `s_fork_block` (proving the scan ran):
```cpp
EXPECT_WAIT_FOR_CONDITION(
    [&]() { return node_main->GetBalance( dest_addr ) >= initial_balance + kNumCatchupBurns * kMintAmount; },
    kCatchupMintTimeout,
    "Catch-up scan must mint all pre-node burns",
    nullptr );
```

### WR-02: Test C double-mint assertion reads balance_before and balance_after back-to-back — trivially equal

**File:** `test/src/bridge_e2e/bridge_anvil_catchup_e2e_test.cpp:685-688`
**Issue:** `balance_before` and `balance_after` are read on consecutive lines with no
intervening sleep, poll, or watcher cycle. They will always be equal, so
`EXPECT_EQ(balance_after, balance_before)` is trivially true and provides zero coverage
for the "no double-mint on second poll" claim. The comment says the production watcher
"must not double-mint on its second poll," but the assertion cannot detect a double-mint
because no poll occurs between the two reads.

**Fix:** Wait for at least one production watcher poll cycle between the two reads, then
assert stability:
```cpp
const uint64_t balance_before = node_main->GetBalance( dest_addr );
// Wait for at least one production watcher poll cycle (poll_interval = 15s).
EXPECT_WAIT_FOR_CONDITION(
    [&]() { return true; },  // let one full poll interval elapse
    kCatchupPollIntervalGate,
    "production watcher poll window",
    nullptr );
const uint64_t balance_after = node_main->GetBalance( dest_addr );
EXPECT_EQ( balance_after, balance_before )
    << "Test C: production watcher must not double-mint on its second poll";
```

### WR-03: FundAccount0WithGnus interpolates anvil_rpc_url into shell commands without IsValidAnvilRpcUrl validation

**File:** `test/src/bridge_e2e/anvil_fixture.hpp:426-463`
**Issue:** `FundAccount0WithGnus` constructs shell commands by string-concatenating
`anvil_rpc_url` into `cast rpc ... --rpc-url <url>` and `cast send ... --rpc-url <url>`
commands (lines 427, 440, 448, 455, 463) without calling `IsValidAnvilRpcUrl`. The
validation exists and is applied in `SendBridgeOutBurn` (line 373), but is missing here.
While current callers always pass `s_anvil.RpcUrl()` (internally constructed as
`http://127.0.0.1:<port>`), the function's public signature accepts any `std::string`,
so a future caller passing a URL with shell metacharacters (`;`, backtick, `$(...)`)
would achieve command injection. This is a defense-in-depth gap.

**Fix:** Add validation at the top of `FundAccount0WithGnus`:
```cpp
static inline bool FundAccount0WithGnus( const std::string &anvil_rpc_url )
{
    if ( !IsValidAnvilRpcUrl( anvil_rpc_url ) )
    {
        spdlog::error( "FundAccount0WithGnus: rejected anvil_rpc_url with disallowed characters: {}",
                       anvil_rpc_url );
        return false;
    }
    // ... rest of function
}
```

### WR-04: AnvilReplayRejection EXPECT_WAIT_FOR_CONDITION checks balance == balance_before_replay — trivially true immediately after the mint call

**File:** `test/src/bridge_e2e/bridge_anvil_e2e_test.cpp:563-567`
**Issue:** When the second mint is NOT rejected (`replay_rejected == false`), the test
waits for `GetBalance(dest_addr) == balance_before_replay`. Since the mint hasn't settled
yet (it was just submitted), the balance is still equal to `balance_before_replay` at the
first poll, so `EXPECT_WAIT_FOR_CONDITION` succeeds immediately. The test then falls
through to `EXPECT_TRUE(replay_rejected)` (line 574) which fails — so the test does
eventually detect the failure, but the intermediate `EXPECT_WAIT_FOR_CONDITION` is
misleading and doesn't actually verify what its description claims ("Balance must not
increase from a replayed Anvil burn tx hash"). If the duplicate mint settles later, the
balance WOULD increase, but the wait condition already passed.

**Fix:** Wait for the balance to potentially increase (give the duplicate mint time to
settle), THEN assert it didn't:
```cpp
if ( !replay_rejected )
{
    // Give any erroneously-accepted duplicate time to settle.
    std::this_thread::sleep_for( std::chrono::milliseconds( 500 ) );
    EXPECT_EQ( s_nodes[0]->GetBalance( dest_addr ), balance_before_replay )
        << "Balance must not increase from a replayed Anvil burn tx hash";
}
```
(Note: `std::this_thread::sleep_for` is acceptable in test code when the wait-condition
pattern cannot express "wait for a non-event." Alternatively, poll for a fixed duration
with `waitForCondition` returning true unconditionally.)

### WR-05: split_host_port does not handle IPv6 addresses in brackets

**File:** `evmrelay/src/eth/rpc_http_transport.cpp:69-88`
**Issue:** `split_host_port` uses `authority.rfind(':')` to find the port separator.
For an IPv6 URL like `http://[::1]:8545`, the authority is `[::1]:8545`. `rfind(':')`
finds the colon before `8545`, yielding `host = "[::1]"` and `port = "8545"`. The host
`[::1]` (with brackets) is then passed to `resolver.resolve("[::1]", "8545")`, which may
fail depending on the resolver's bracket handling. No current code uses IPv6 RPC URLs,
but the function silently misparses them rather than rejecting them.

**Fix:** Detect bracketed IPv6 hosts and handle them separately:
```cpp
if ( !authority.empty() && authority.front() == '[' )
{
    const auto close_bracket = authority.find( ']' );
    if ( close_bracket == std::string_view::npos )
    {
        return std::nullopt;
    }
    const auto host = authority.substr( 1, close_bracket - 1 ); // without brackets
    if ( close_bracket + 1 == authority.size() )
    {
        return std::pair{ std::string( host ), is_https ? "443" : "80" };
    }
    if ( authority[close_bracket + 1] != ':' )
    {
        return std::nullopt;
    }
    const auto port = authority.substr( close_bracket + 2 );
    if ( port.empty() ) { return std::nullopt; }
    return std::pair{ std::string( host ), std::string( port ) };
}
```

### WR-06: CA certificate load failures are silently ignored — TLS verification may fail with no diagnostic

**File:** `evmrelay/src/eth/rpc_http_transport.cpp:122-147`
**Issue:** In `read_https_response`, `ssl_ctx.set_default_paths(ec)` (line 122),
`ssl_ctx.load_verify_file(env_cert_file, load_ec)` (line 129), and
`ssl_ctx.load_verify_file(ca_path, load_ec)` (line 145) all silently discard their error
codes. If `SSL_CERT_FILE` points to an invalid file AND all fallback CA paths are missing
(e.g., minimal container/CI environment), the ssl_ctx has NO trusted CAs loaded. TLS
verification (`verify_peer = true`, the default) will then fail at `stream.handshake()`
with a cryptic "certificate verification failed" error, with no log indicating that CA
loading failed. The user has no way to diagnose why HTTPS requests fail.

**Fix:** Log a warning when CA loads fail, and track whether at least one load succeeded:
```cpp
bool any_ca_loaded = false;
boost::system::error_code ec;
ssl_ctx.set_default_verify_paths( ec );
if ( !ec ) { any_ca_loaded = true; }

// SSL_CERT_FILE
if ( env_cert_file && env_cert_file[0] != '\0' )
{
    boost::system::error_code load_ec;
    ssl_ctx.load_verify_file( env_cert_file, load_ec );
    if ( load_ec ) { logger->warn( "Failed to load SSL_CERT_FILE {}: {}", env_cert_file, load_ec.message() ); }
    else { any_ca_loaded = true; }
}
// ... same for fallback paths ...
if ( !any_ca_loaded && options.verify_peer )
{
    logger->warn( "RpcHttpTransport: no CA certificates loaded — TLS verification will fail" );
}
```

### WR-08: find_contract_creation_blocks.py binary_search_creation returns None on pruned historical state, leaving creation_block = 0 — config silently lacks the floor

**File:** `scripts/find_contract_creation_blocks.py:178-181`
**Issue:** When `eth_get_code` returns None (RPC unavailable at a historical block due to
pruning), `binary_search_creation` returns None, and the main loop (line 387-389) prints
"FAILED to find creation block" and increments `errors`. But the config file is still
written (line 392-396) with `creation_block = 0` for chains that succeeded, while the
failed chain keeps its old value (0 if never set). A chain with `creation_block = 0` in
the config means the `BridgeCatchupWatcher` falls back to `config_.start_block` as the
scan floor, which could be genesis — causing the watcher to scan millions of blocks and
hit rate limits. The script should either fail loudly (exit non-zero, which it does) or
write a sentinel value that the C++ code can distinguish from "never attempted."

The current behavior is partially correct: `sys.exit(1)` on errors (line 400) means CI
fails. But if the script is run manually and the error is ignored, the config silently
has `creation_block = 0`.

**Fix:** This is acceptable as-is for CI (exits non-zero). For manual runs, add a
post-run summary that explicitly lists chains with `creation_block = 0`:
```python
print("\nSummary:")
for chain_name, chain_data in config.items():
    if chain_name.startswith("_"):
        continue
    cb = chain_data.get("creation_block", 0)
    if cb == 0:
        print(f"  WARNING: {chain_name} has creation_block = 0 — watcher will scan from genesis")
```

## Info

### IN-01: RpcHttpTransport retry backoff shift (1ull << attempt) is UB for attempt >= 64

**File:** `evmrelay/src/eth/rpc_http_transport.cpp:380`
**Issue:** `1ull << attempt` is undefined behavior when `attempt >= 64` (shifting by the
type width). The default `retry_count = 3` makes this unreachable, but a caller setting
`retry_count >= 64` would trigger UB. The `kMaxRetryBackoffMs` cap mitigates the practical
impact, but the UB is technically present.

**Fix:** Clamp the shift amount:
```cpp
const auto shift = std::min( attempt, 63u );
const auto raw_backoff = options_.retry_backoff.count() * ( 1ull << shift );
```

### IN-02: watch() reads `running` bool without holding running_mutex — technically a data race

**File:** `src/watcher/impl/bridge_catchup_watcher.cpp:68`
**Issue:** `while ( running )` reads the `running` bool (inherited from
`MessagingWatcher`) without holding `running_mutex`. The base class
`MessagingWatcher::stopWatching()` sets `running = false` under the lock. Under the C++
memory model, this is a data race (non-atomic read/write on a non-guarded variable).
This is the established pattern from the base class (`MessagingWatcher::watch()` at
`messaging_watcher.cpp:50` does the same), so it's a pre-existing issue, not introduced
by Phase 04.1.

**Fix:** Make `running` an `std::atomic<bool>` (would require changing the base class),
or read it under the lock in the derived `watch()`.

### IN-03: std::getenv("SSL_CERT_FILE") is not thread-safe if another thread calls setenv

**File:** `evmrelay/src/eth/rpc_http_transport.cpp:125`
**Issue:** `std::getenv` is not thread-safe if another thread calls `setenv`/`putenv`
concurrently. In practice, env vars are set at process start and never modified, so this
is safe. But it's technically a data race per the C++ standard.

**Fix:** Acceptable as-is for the current usage pattern. If strict thread-safety is
required, read the env var once at process start and cache it.

### IN-04: CMake custom target find_contract_creation_blocks uses bare `python3` without find_program

**File:** `src/account/CMakeLists.txt:169`
**Issue:** The custom target invokes `python3` directly. If `python3` is not on PATH
(e.g., systems where only `python` exists), the target fails with a cryptic "command not
found" error rather than a clear CMake configuration error.

**Fix:** Use `find_program(PYTHON3_EXECUTABLE python3)` and fall back to `python`:
```cmake
find_program(PYTHON3_EXECUTABLE NAMES python3 python)
if(NOT PYTHON3_EXECUTABLE)
    message(FATAL_ERROR "python3 not found — required for find_contract_creation_blocks")
endif()
add_custom_target(find_contract_creation_blocks
    COMMAND ${PYTHON3_EXECUTABLE} ...
)
```

### IN-05: find_contract_creation_blocks.py does not validate the `--rpc` override URL format

**File:** `scripts/find_contract_creation_blocks.py:291-297`
**Issue:** The `--rpc chain_name=URL` override splits on `=` and uses the URL directly
in `urlopen`. There's no validation that the URL is a valid HTTP(S) URL. A malformed URL
would cause a runtime `URLError` (caught by `rpc_call`), but the error message would be
cryptic. This is a minor usability concern for the build script.

**Fix:** Optional — add a basic URL format check:
```python
if not url.startswith(("http://", "https://")):
    print(f"Invalid RPC URL for {name}: {url} (must start with http:// or https://)", file=sys.stderr)
    sys.exit(1)
```

<interfaces>
From src/blockchain/Consensus.cpp:
- `FilterCertificate` rejects malformed/legacy-key-invalid/rejected certificates before callback work.
- `CertificateReceived` is reached from the CRDT put hook before `CrdtSet::PutElems` commits RocksDB; in this phase it is a notification path that marks its certificate work `Stalled` with no future lease for replay, and it never releases an active vote.
- `HandleCertificate` is PubSub/keyless and calls volatile `ClearProposalSlot`; it is not a durable-release hook.
- `ClearProposalSlot` removes only current process bookkeeping and must remain separate from active-vote record deletion.
- `RecoverPendingCertificateWork`, invoked at manager construction and round-timer startup/recovery, is the post-commit release path: it must `db_->Get` the already-existing live legacy `/cert/<subject-hash>` value, revalidate its legacy key/binding, require `ValidateCertificate(...) == Check::Approve`, derive `GetSlotKey(certificate.proposal())`, then release a matching active vote and clear volatile slot state.
- Phase 8 keeps accepted certificate storage/lookup at legacy `/cert/<subject-hash>` while `GetExpectedCertificateSlotKey` is validation only; Phase 9 must not make `/cert/<slot>` authoritative.

From src/crdt/impl/crdt_datastore.cpp and src/crdt/crdt_callback_manager.hpp:
- `CrdtSet::SetValue` invokes the callback before `CrdtSet::PutElems` commits RocksDB. Callback receipt therefore cannot establish durability; a failed or racing post-callback readback must retain both the active vote record and stalled certificate work for retry.

From Plan 09-01:
- Active votes reside only in direct local RocksDB under `/consensus/vote/<canonical-slot>` and are retained after deadline.
- Candidate admission and startup recovery must consult the finalized-slot seam before any vote creation/reannouncement.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| accepted legacy certificate records → finalized-slot query | Existing CRDT values are read to establish local no-revote safety without gaining certificate authority. |
| certificate filter/callback/handler → active-vote removal | An externally supplied certificate event can request deletion of a safety lock. |
| timer/candidate admission → released/finalized state | Late candidates can race expiry, recovery, and certificate processing. |
| local RocksDB active-record read/write/remove | Corruption or failure must never create a usable vote or silently unlock. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-01 | Tampering | active-vote record recovery | mitigate | Keep Plan 01 parse/coherence/signature validation in every restore path; corrupt local data is unusable and does not authorize a new vote. |
| T-09-02 | Tampering / Repudiation | same-slot record collision | mitigate | Retain byte-exact persist-or-load semantics and test that certificate/expiry paths cannot overwrite an occupied record with another vote. |
| T-09-03 | Replay | deadline/retry/release interaction | mitigate | Preserve expired records and locks; retries cease at deadline, and release requires accepted same-slot finality rather than replay/expiry state. |
| T-09-04 | Tampering / Elevation | `CertificateReceived` and `ReleaseActiveVoteForAcceptedSlot` | mitigate | Verify key, certificate, registry/handler acceptance, and proven durable ingress ordering before same-slot direct-local removal; reject/stall/receipt/PubSub paths never remove. |
| T-09-05 | Denial of Service / Race | candidate window and finalized-slot gate | mitigate | Lock admission/freeze/release state, consult finalized-slot read seam before voting, and regression-test candidates arriving at deadline under a reconstructed manager. |
| T-09-SC | Tampering | dependency supply chain | accept | No package-manager installation or new dependency is permitted in this phase. |
</threat_model>

<objective>

registered CRDT key (D-03) and the reader-side logic that always re-derives trust from
`value + sig/*` entries rather than trusting any "final" marker (D-04). This closes SCRDT-03

via CRDT puts + filter callbacks only, no new networking).

(TrustedPeerRegistry, BurnConfig, migrated ValidatorRegistry) writes through this wrapper and
nothing else.

gate and the full propose+sign+quorum sequence against a single-node `GlobalDB`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Any local caller -> `GlobalDB::Put` on a registered key | The single most safety-critical boundary in this phase: local writes bypass `RegisterElementFilter` entirely (`crdt_datastore.cpp`, `!created_by_self`), so `SecureCrdt::ProposeValue`/`AddSignature` are the ONLY code this phase introduces that may call `Put` on a registered key. |
| Remote peer delta -> local CRDT merge | Untrusted network input; the filter callback registered in `RegisterFilters()` is the synchronous pre-merge veto point, running inline on the DAG-sync worker thread. |
| Reader (any node, any time) -> claimed-trusted value | No CRDT entry is ever self-certifying; every reader must independently run `ReadIfQuorum`'s value+sig/*+EvaluateQuorum re-derivation (D-04) — a node must never cache "this was final" across a value change. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-05 | Tampering / Elevation of Privilege | Any code path calling raw `GlobalDB::Put` on a registered key, bypassing `SecureCrdt` | mitigate | D-03's mandatory-wrapper architecture: this plan introduces ZERO other call sites to `Put` for registered keys; acceptance criteria greps `SecureCrdt.cpp` to confirm `Put` only appears inside `ProposeValue`/`AddSignature`. Future phases (10-12) are constrained by code review to route all registered-key writes through `SecureCrdt`, never `GlobalDB` directly. |
| T-09-06 | Tampering | Duplicate-signature padding to fake quorum | mitigate | Delegated entirely to `multisig::EvaluateQuorum`'s dedup-before-verify-per-address logic (Phase 8, shipped and already tested) — `SecureCrdt` never re-implements counting/dedup itself (acceptance criteria greps for the `EvaluateQuorum` call). |
| T-09-07 | Tampering | Signature replay: an old valid signature reused against a newly-proposed value at the same `base_key` | mitigate | `ReadIfQuorum` and `AddSignature`'s local gate both pass the CURRENT value's bytes (fetched fresh via `db_->Get(base_key)` each call) as the `payload` to `VerifyPayloadSignature`/`EvaluateQuorum` — never a cached/stale value — so a signature over an old value fails verification against the new value automatically (D-04's re-derivation model). |
| T-09-08 | Denial of Service | Malformed/oversized payload in `ISignedCRDTData::DeserializeFromBytes` or the filter's base-key element handling | mitigate | Codec methods return `bool`/`outcome::result` rather than throwing (per Plan 01's interface contract); the filter callback rejects (returns empty vector) on any parse failure rather than propagating an exception onto the DAG-sync worker thread, mirroring `ValidatorRegistry::FilterRegistryUpdate`'s parse-failure-rejects pattern. |
| T-09-09 | Information Disclosure | `QueryKeyValues` enumerating all `sig/<addr>` rows | accept | Signer addresses and their signatures over a given value are not confidential data in this system's threat model — CRDT-replicated data is inherently visible to all peers with read access; no new disclosure introduced. |

</threat_model>

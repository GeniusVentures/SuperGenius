<interfaces>
`ProcessDueVoteWork` freezes a slot's eligible candidates, chooses `IsBetterProposal`'s deterministic winner, calls `PersistOrLoadExactActiveVote` before queuing publication, then emits the exact stored signed vote through `SubmitVote`. The persisted record is `/consensus/vote/<slot>` in the validator's local datastore; test validators therefore need separate local datastores. `PersistOrLoadExactActiveVote` rejects a non-byte-identical replacement and `RecoverActiveVotes` restores only a valid exact signed record after restart.

`CreateCertificate(proposal, votes)` calls `TallyVotes` for that one proposal only. It counts valid, distinct voter signatures whose `vote.proposal_id()` equals the supplied proposal; it has no global vote history and cannot detect a voter who signed a second proposal in a different certificate. With this plan's three-validator, 2-of-3 snapshot, two different same-slot 2-of-3 quorum sets overlap, making such a second quorum an equivocation/consensus-fault signal rather than an alternative authority or a Mint recovery branch.

`CrdtSet::SetValue` already applies `ConvergentImmutablePriority` by retaining the lexicographically lower lowercase SHA-256 serialized value. `SubmitCertificate` duplicates this comparison locally; `FilterCertificate` currently validates only. This plan shares that exact comparison in `Consensus.cpp`, then makes FilterCertificate read a pre-existing canonical key after basic validation. It must not alter `CrdtSet`, `CrdtDatastore`, protobuf schemas, vote/certificate canonicalization, `TransactionManager`, or the receive-only PubSub path.

For Mint-specific fault logging, decode each already-validated certificate's `NonceSubject` with `DecodeNonceSubject`, require a nonempty `tx_hash`, and inspect the embedded transaction oneof before treating it as Mint evidence. Compare exact `tx_hash` values only after both sides are verified Mint V2 subjects. Do not infer an equivocation from serialized certificate bytes, vote order/subset, proposal representation, or different valid certificate encodings for the same exact Mint transaction.
</interfaces>

## Trust Boundaries

| Boundary | Description |
|---|---|
| validator-local proposal lifecycle -> signed vote publication | An honest node must persist exactly one signed choice for a canonical slot before any vote can be observed by peers. |
| remote CRDT element -> existing `/cert/<slot>` value | Untrusted remote certificate bytes cross validation and deterministic selection before CRDT materialization. |
| valid same-slot Mint certificates -> operational diagnosis | A second valid quorum for a different exact Mint is a validator-equivocation signal, not evidence that certificate selection can repair already-applied effects. |

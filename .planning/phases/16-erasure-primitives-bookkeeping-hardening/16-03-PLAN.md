<objective>
Compose the atomic two-level erase behind the single GlobalDB facade API (D-01): `GlobalDB::EraseEntry(key, cid)` runs the D-C5 guard ensemble (head of any topic via `GetCRDTHeadList`, `IsRootCIDPendingOrActive`, `IsCIDInCache`, `isResolved`), stages the three owner contributions — `CrdtSet` entries via the CrdtDatastore forwarder (16-01), the raw block key via `StageBlockRemoval` (16-02), the node-local raw map key — into ONE `BufferBatch`, commits once with sync, and re-asserts `isResolved` post-commit. Plus the two wiring prerequisites research identified: `GlobalDB` gains the `m_dagSyncer` member (today a local variable in `Init`), and a test-only interruption seam (D-03). On the transaction side, `TransactionManager::EraseTransactionEntry` completes the map's deletion lifecycle (D-C4): resolve CID, atomic erase, revert-free tracked-map cleanup.

Purpose: PRUNE-02's "one atomic WriteBatch" and the "wrong deletion impossible by API shape" principle both land here — guards inside the API, key-layout knowledge inside the owner modules, GlobalDB only composes. Zero production behavior change: no production caller exists (SC-5); behavioral proof lands in 16-04.

Output: Modified globaldb + TransactionManager sources. All new methods tested end-to-end in 16-04; this plan's gates are build + function-scoped source scans.

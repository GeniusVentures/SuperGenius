Mechanism facts verified in current source this planning session (executor should re-confirm while editing):
- getBackoffTimeout is private static (graphsync_dagsyncer.cpp:820-843, declared hpp:165), returns SECONDS: ever_connected base 5 cap 30; never-connected base 10 cap 1800.
- The blacklist clock is second-granularity: AddToBlackList uses GetCurrentTimestamp() at :801; IsOnBlackList at :858 compares now - entry.timestamp > timeout (:870). GetCurrentTimestamp (:1017-1022) is duration_cast<seconds>. Sub-second configuration therefore REQUIRES converting the blacklist subsystem to milliseconds. GetCurrentTimestamp itself must NOT change — cid_failures_ (RecordCIDFailure :1024, HasRecentCIDFailure :1034 with its 180-second recency window, ClearCIDFailure :1061) stays on the seconds clock, untouched.
- fetchGraph's route loop has TWO skip mechanisms (graphsync_dagsyncer.cpp:213-233): IsOnBlackList → log line "Skipping blacklisted peer" (:222), and HasRecentCIDFailure → log line "Skipping peer ... due to recent CID-specific failure" (:229-230). On RequestState::FAILED with a connection-failure status (RS_CANNOT_CONNECT etc., IsConnectionFailureStatus :1075-1081) the peer is blacklisted (BlackListPeer :337, warn line "Blacklisting peer and trying fallback" :332-333); non-connection failures record a CID failure (:344). Route exhaustion logs "No usable route candidates left for CID" (:388). The hypothesis verdict MUST distinguish these two skip mechanisms by log line — if the focused runs still fail while "due to recent CID-specific failure" is the operative skip, the blacklist hypothesis is disproven for that mechanism and the finding feeds 12-19.
- RestartPeer (multi_node_finality_fault_test.cpp:1040-1054) recreates the peer from the same root: same keypair (same PeerId), same port. The fetchers' GraphsyncDAGSyncer instances are never restarted, so their blacklist entries against the reused identity persist — which is why the seam must be STATIC (process-wide) rather than per-instance: the test cannot reach the fetchers' syncer instances inside GlobalDB.
- The four peers run in ONE process (D-01), so a static override set in the RestartAtVote body covers all fetchers.

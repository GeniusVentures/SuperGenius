<objective>
Close the "Role::FULL is never assigned" gap (RESEARCH Pitfall 2). Add an algorithmic promotion rule inside the existing `ApplyVoteEffects` so a REGULAR validator that accumulates enough reputation (weight) with low penalty is promoted to FULL. The FULL role's higher max-weight cap then flows naturally into the slot tally via `EvaluateSlotQuorum` (no Plan 02 change required — D-08).

Purpose: FULL nodes carry higher weight, which strengthens the DIRECT_API cohort over time. Without this, the DIRECT_API cohort depends entirely on configured paid endpoints; promotion adds an organic reputation path. This plan is logically independent of Plan 02's tally logic (D-08: promotion operates on weight, the tally reads weight) but is serialized in Wave 3 because both plans edit `ValidatorRegistry.{hpp,cpp}`.

Output:
- `WeightConfig::full_promotion_weight_` constant (default tunable).
- Promotion branch in `ApplyVoteEffects` (REGULAR → FULL when weight ≥ threshold and penalty < penalty_threshold_).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Consensus participation → Validator role | `ApplyVoteEffects` is invoked after certificate finalization; crossing this boundary mutates persistent validator state (role). A flawed promotion rule could elevate a malicious or sybil node to FULL. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-11 | Elevation of Privilege | REGULAR -> FULL promotion | mitigate | Promotion requires BOTH weight accumulation (earned via correct votes over time) AND low penalty (`penalty_score < penalty_threshold_`). A sybil attacker starting at weight 1 needs many correct consensus rounds to reach `full_promotion_weight_` (default 500), during which any misbehavior accumulates penalty and blocks promotion. Combined with the slot tally (Plan 02), a promoted FULL node still cannot capture a bridge mint alone — it must also have a paid RPC endpoint for slot 0, or be one of ≥2 PUBLIC voters sharing a hash. |
| T-06-12 | Tampering | Promotion bypass via penalty reset | mitigate | The penalty gate uses the post-decrement `penalty_score()` in the approve branch. A node cannot trivially reset penalty to promote — penalty decrements by 1 per approve (line 1734), so a penalized node must earn back reputation over many rounds. |
| T-06-13 | Repudiation | Non-deterministic promotion across peers | mitigate | `ApplyVoteEffects` is a pure function of `(entries, registered_votes, weight_config_)`. Same inputs → same role mutation. No node-local state. Peers converge via the registry CRDT. |
| T-06-14 | Tampering | GENESIS demotion | mitigate | The `entry.role() == Role::REGULAR` guard prevents GENESIS from being rewritten to FULL. GENESIS authority is preserved. |
| T-06-SC | Tampering | No third-party packages | accept | Pure C++ against existing stack. No package installs. |

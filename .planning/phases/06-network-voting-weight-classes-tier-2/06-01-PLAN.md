<objective>
Add cohort classification to the validator registry so the consensus layer can partition voters into DIRECT_API vs PUBLIC_ONLY cohorts for Tier-2 bridge-mint voting.

This plan delivers the **classification primitive only**. It does NOT change quorum arithmetic (Plan 06-02) or add Role::FULL promotion (Plan 06-03). It closes the foundational gap identified in the research: the cohort signal exists in `RpcEndpointConfig` (`is_paid`/`api_key_*`) but is never propagated to the consensus/registry layer where cohort membership must live.

Purpose: Without deterministic cohort membership, the two-tier quorum policy in Plan 06-02 has nothing to partition. Without registry-stored classification, peers would disagree on cohort (Pitfall 5).

Output: `ValidatorCohort` enum, `ValidatorEntry.cohort` proto field, `ValidatorRegistry::CohortOf()`, `PublicChainInputValidator::HasDirectApiEndpoint()`, and GeniusNode self-classification wiring.
</objective>

<decisions>
Open questions resolved (from 06-RESEARCH.md):

**A2 (node-level vs per-chain self-classification):** NODE-LEVEL. A node with ANY paid/api-key endpoint across ANY chain self-classifies as DIRECT_API. This is the simplest deterministic rule and matches the design note's framing ("nodes with API-key-based direct RPC connections"). Per A2 recommendation.

**A3 (Role::FULL promotion mechanism):** This plan stores the cohort signal **independently of Role** via a new `cohort` proto field. Role::FULL promotion is a separate concern handled in Plan 06-03. Rationale: Pitfall 2 warns against deriving cohort primarily from Role::FULL on day one (FULL is never assigned). Cohort is derived from RPC config presence at self-registration time, making the DIRECT_API cohort non-empty from genesis if any node has a paid endpoint.

**A6 (genesis authority cohort):** Genesis authority (Role::GENESIS) is implicitly DIRECT_API. Genesis is the highest-trust role; classifying it as PUBLIC_ONLY would make bridge mints stall.
</decisions>
</context>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local RPC config → registry | A node's own RPC config determines its self-classification. A malicious node could falsely self-classify as DIRECT_API. Mitigation: self-classification is stamped into the registry; cohort weight is bounded by registry `weight`/`Role` caps (sybil resistance). Reputation promotion in Plan 06-03 adds an independent signal. |
| CRDT replication | Cohort field replicates to all peers. Malicious cohort values are bounded by existing registry signature verification (RegistryUpdate signatures). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Spoofing | Self-registration cohort field | mitigate | Cohort is a derived classification, not an authority claim. A node falsely claiming DIRECT_API gains cohort membership but its vote weight is still bounded by registry `weight` (capped by Role and ApplyTotalWeightCap). The two-cohort AND rule in Plan 06-02 still requires the OTHER cohort to independently agree. |
| T-06-02 | Tampering | ValidatorEntry.cohort proto field | mitigate | Registry updates are signed (existing `RegistryUpdate.signatures`); tampering with cohort post-replication is detected by signature verification in `VerifyUpdate`. |
| T-06-03 | Repudiation | Non-deterministic cohort across peers | mitigate | CohortOf() is a pure function of registry state (Pitfall 5 rule). All peers derive identical cohort from identical registry snapshots. Test REQ-DETERM-01 covers this in Plan 06-04. |
| T-06-04 | Information disclosure | Self-classification logging | accept | Cohort membership is not sensitive (not a secret). spdlog info-level logging is consistent with existing registry logging. |
| T-06-05 | Elevation of privilege | Genesis implicit DIRECT_API | accept | Genesis authority is the highest-trust role by design (existing GetAuthorizedFullNodeAddress pattern). Implicit DIRECT_API is consistent with this trust model. |
</threat_model>

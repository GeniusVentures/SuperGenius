<objective>
Establish the cryptographic foundation of the slot-based RPC-hash voting model (D-01). Extend the `ConsensusVote` proto with three slot-hash fields and wire the node to populate them from its own RPC endpoint configuration at vote-construction time.

Purpose: Without these fields in the proto and the signing surface, no later tally can deduplicate by hash (D-03) or attribute 50/25 weight (D-02). This is Wave 1 foundation; Plan 02 consumes the fields. Plan 03 (FULL promotion) is independent of this plan's tally logic but shares the ValidatorRegistry file ownership pattern.

Output:
- `Consensus.proto` with `slot_0_hash`, `slot_1_hash`, `slot_2_hash` on `ConsensusVote`.
- `PublicChainInputValidator` helpers that hash a configured endpoint (Tier 1 already classifies paid vs. public — reuse that classification; D-10 keeps Tier 1 unchanged).
- `GeniusNode::PopulateVoteSlotHashes()` invoked wherever a vote is created/signed.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Node → Network (vote broadcast) | Outgoing `ConsensusVote` crosses this boundary; the slot hashes must be committed under the vote signature so peers can detect tampering. |
| Config → Vote population | The node's local `RpcEndpointConfig` (from `chains_config.json`) drives slot population; a misconfigured or attacker-controlled config could populate wrong hashes. Mitigated by Tier 1 (D-10) which independently verifies endpoints. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Tampering | ConsensusVote slot hashes | mitigate | Slot hashes are inside the `VoteSigningBytes` signing surface (only `signature` is cleared). Any mutation invalidates the signature. Verified by Task 1 behavior test. |
| T-06-02 | Spoofing | GeniusNode PopulateVoteSlotHashes | mitigate | Hashes are carried inside the node's own secp256k1-signed vote; a node cannot forge another validator's slot hash without that validator's private key. |
| T-06-03 | Information Disclosure | HashDirectApiEndpoint URL hashing | accept | The hash is SHA-256 of the URL template; it does not reveal the API key (only the URL is hashed, never the key — key material stays in `api_key_*` fields and is never serialized into the vote). |
| T-06-04 | Repudiation | Empty-bytes abstain sentinel | mitigate | Empty slot hashes are explicitly documented as abstention (D-05); the tally in Plan 02 treats empty as "did not vote this slot", not as a vote for a zero hash. Solo all-zero-hash votes cannot inflate a slot group. |
| T-06-SC | Tampering | No third-party packages installed | accept | Pure proto + internal-hasher change; no npm/pip/cargo. slopcheck N/A. |
</threat_model>

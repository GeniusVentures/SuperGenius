<objective>
Add the two-tier (dual-cohort AND) quorum policy for bridge-mint subjects and route BOTH quorum evaluation sites (`TallyVotes` for certificate creation AND the incremental `HandleVote` tally) through one shared `EvaluateQuorum` helper. This is the core security deliverable of Phase 6: an attacker must corrupt nodes in BOTH cohorts simultaneously to mint fake bridge tokens.

Purpose: The existing single-pool 2/3 quorum cannot prevent a quorum of colluding validators from minting fake bridge tokens (ROADMAP "Consensus Trust Model for Bridge Mints"). The two-cohort AND rule raises collusion cost by requiring independent agreement across the DIRECT_API and PUBLIC_ONLY cohorts. Pitfall 1 (modifying only one tally site) is the primary failure mode this plan must avoid.

Output: `TwoTierQuorumPolicy` in ValidatorRegistry, shared `EvaluateQuorum` in ConsensusManager, both tally sites unified, `WeightConfig` extended with cohort thresholds.
</objective>

<decisions>
Open questions resolved (from 06-RESEARCH.md):

**A1 (extend ConsensusCertificate proto?):** NO. Keep certificate single-pool in v1. Cohort breakdown stays in the in-memory `QuorumTally` extension only. The certificate `total_weight`/`approved_weight` fields continue to carry single-pool totals (sum of both cohorts). Rationale: changing the certificate schema breaks all peers and risks consensus divergence (research Anti-Patterns). The cohort AND-predicate is evaluated BEFORE certificate creation; the certificate itself records the outcome, not the breakdown.

**A4 (50%/25% semantics):** These are NOT per-vote multipliers and NOT quorum thresholds themselves. Per the design note's "Require ≥51% of this cohort to approve" sentence, the cohort membership carries the weight class distinction (DIRECT_API nodes are higher-trust, PUBLIC_ONLY are lower-trust), and EACH cohort independently requires ≥51% of ITS OWN total cohort weight to approve. So: cohort membership partitions the validator set; per-cohort quorum threshold is 51% (configurable). The 50%/25% vocabulary in the goal describes the weight-class distinction inherited from Tier 1, not a separate Tier-2 multiplier. This is the safest interpretation and matches the design note most directly.

**A5 (per-cohort threshold):** Both cohorts use an independent configurable threshold. Default 51/100 for each (configurable via WeightConfig). Genesis authority is in the DIRECT_API cohort but its weight still counts toward that cohort's total.

**Fail-closed on empty cohort:** If either cohort has zero total weight (e.g., no PUBLIC_ONLY validators exist on a private testnet), the two-tier policy fails-closed — no certificate. This is a deliberate safety choice: an empty cohort cannot "independently agree." For dev/testnets without both cohorts, the operator sets a config flag to disable two-tier (see Task 2). Production mainnet MUST run with both cohorts populated.
</decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Subject payload → quorum policy | The subject discriminator (IsBridgeMintSubject) gates which policy applies. A malformed subject that fails to deserialize is treated as non-bridge (single-pool) — fail-safe for liveness of internal transfers. |
| Vote tally → certificate | The two-tier AND predicate sits between accumulated votes and certificate production. This is the core security boundary this phase adds. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-06 | Tampering | Bridge-mint certificate production | mitigate | Two-cohort AND predicate (T-06 core security control). Attacker must corrupt nodes in BOTH DIRECT_API and PUBLIC_ONLY cohorts. Single-cohort collusion cannot mint. |
| T-06-07 | Denial of service | Bridge-mint stall from empty cohort | mitigate | Fail-closed when a cohort has zero weight (deliberate safety default). Dev/testnet escape via two_tier_quorum_disabled_ flag. Production MUST populate both cohorts (documented). |
| T-06-08 | Tampering | Weight overflow in cohort accumulation | mitigate | uint64_t with saturation. AccumulateCohortWeights uses the same uint64_t pattern as existing TotalWeight (ValidatorRegistry.cpp:297-305). |
| T-06-09 | Repudiation | Divergent quorum between TallyVotes and HandleVote | mitigate | Single EvaluateQuorum helper called by both sites (Pitfall 1). REQ-QUORUM-05 test in Plan 06-04 verifies agreement. |
| T-06-10 | Elevation of privilege | Sybil flooding PUBLIC_ONLY cohort | accept | Per-cohort weight bounded by registry Role/weight caps and ApplyTotalWeightCap (existing). Reputation promotion (Plan 06-03) gates DIRECT_API. Accepting residual risk: sybil resistance is a registry-layer concern, not a quorum-policy concern. |

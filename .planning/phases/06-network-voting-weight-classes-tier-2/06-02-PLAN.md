<objective>
Implement the slot-based cumulative quorum algorithm (D-06) and route BOTH tally sites through one shared helper (RESEARCH Pitfall 1). This is the riskiest plan: it touches shared consensus hot paths. Slot 0 = 50% per qualifying voter (D-02); slots 1-2 = 25% per qualifying voter with ≥2-validator hash-group deduplication (D-03); certificate iff cumulative `qualified_sum > 0.75 * total_voting_reputation`.

Purpose: This is the security core of Phase 6 — the cumulative slot tally raises the cost of fabricating a bridge mint (an attacker must corrupt DIRECT_API weight AND multiple PUBLIC validators sharing an endpoint hash). Single-pool quorum for non-bridge subjects is preserved unchanged.

Output:
- `ValidatorRegistry::EvaluateSlotQuorum()` — the deterministic slot-tally arithmetic (hash grouping, dedup, 50/25 weighting, 75% threshold).
- `ConsensusManager::EvaluateQuorum()` — dispatcher that picks single-pool (`IsQuorum`) vs slot (`EvaluateSlotQuorum`) based on subject type.
- Both `TallyVotes` (certificate creation) and the `HandleVote` incremental tally routed through `EvaluateQuorum` for bridge mints.
- `QuorumTally` extended with `qualified_sum` and `slot_threshold` for observability.
</objective>

<decisions>
This plan implements the slot-tally arithmetic and the dual-tally-site routing:
- **D-02 (LOCKED):** Slot 0 contribution is `voter.weight * 0.50` for each distinct voter with a non-empty `slot_0_hash`. A single valid hash suffices (no dedup for slot 0 — DIRECT_API trust comes from the API key + reputation).
- **D-03 (LOCKED):** Slots 1 and 2 each: group votes by `slot_N_hash`, discard groups with `< slot_public_min_group_` (default 2) distinct validators, sum the weight of voters in qualifying groups, multiply by 0.25. Solo hashes contribute zero.
- **D-05 (LOCKED):** A voter with all three slot hashes empty still counts toward `total_voting_reputation` (they cast an approve) but contributes zero to `qualified_sum`. This is fail-closed: an RPC outage raises the threshold without helping to meet it. (An all-abstain node should not even broadcast per Plan 01 Task 3, but the tally is robust to it.)
- **D-06 (LOCKED):** Single cumulative tally. `qualified_sum = sum(slot contributions)`. `threshold = total_voting_reputation * 0.75`. Certificate iff `qualified_sum > threshold`. STRICT greater-than (matches CONTEXT.md pseudocode `certificate_produced = (qualified_sum > threshold)`).
- **D-07 (LOCKED):** Reputation = existing `ValidatorEntry.weight`. No new scoring; the existing weight (accumulated via `ApplyVoteEffects`) is the reputation input.
- **REQ-DETERM-01 (LOCKED):** The tally reads ONLY from the vote set and the registry snapshot. It does NOT consult any per-peer local RPC state. All peers with the same inputs compute the same output.
</decisions>

    Algorithm (matches CONTEXT.md D-06 pseudocode exactly):
    1. Build a list of `(voter_id, weight, slot_0_hash, slot_1_hash, slot_2_hash)` for each vote where: (a) the voter is found in `registry` via `FindValidator`, (b) `status == ACTIVE`, (c) the vote is an approve vote. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Network → ConsensusManager (vote ingestion) | Votes arrive from peers; the tally must treat all vote data (including slot hashes) as untrusted until signature-verified. |
| Tally → Certificate production | Crossing this boundary promotes a proposal to a certificate; the slot model is the access-control predicate that gates this (ASVS V4). |
| Peer A tally ↔ Peer B tally | Consensus requires both peers to reach the same `has_quorum` for the same inputs — determinism is a security property (REPUDIATION category if violated). |

| T-06-05 | Elevation of Privilege | Slot tally (bridge mint approval) | mitigate | D-03 ≥2-validator dedup on slots 1-2 prevents a single PUBLIC endpoint from capturing slot weight.

### CR-04: Preserving UNCONFIRMED transactions skips ordinary funding-reservation cleanup

**Classification:** BLOCKER

**File:** `/Users/henriqueklein/gnus/SuperGNUS/src/transaction/TransactionManager.cpp:5971-5976`

**Related:** `TransactionManager.cpp:2135-2147`, `2377-2384`, `1507-1510`, `5941-5961`, `6020-6022`; `src/account/UTXOManager.cpp:635-661`, `703-725`; `TransactionConsensusHandler.cpp:82-92`.

**Issue:** The new send-failure rollback flag uses `IsTerminalTransactionStatus`, whose existing wait-completion contract includes `UNCONFIRMED`. An ordinary outgoing Transfer reserves its inputs before enqueue (`TransactionManager.cpp:731`); escrow holds do likewise (`1201`). When an inconclusive proposal timeout moves the queued/progressed transaction from VERIFYING to UNCONFIRMED, that transition releases its nonce but calls only `ReleaseBridgeMintReservation`. That helper returns immediately for every non-`mint-v2` transaction (`5681-5685`), so ordinary funding remains RESERVED. The new batch retirement path calls `RollbackTransactions`, which now passes `preserve_terminal=true`; the guard above then skips the existing matching ordinary `RollbackUTXOs` cleanup. `TickOnce` treats the retirement as success and pops the queued item (`656`). The released nonce can be reused while the original funding remains unavailable to later transfers for the lifetime of this manager state.

**Concrete reproduction:** Reserve an ordinary account-owned input through TransferFunds (or HoldEscrow), retain its queued item, advance it to VERIFYING through the existing incoming/proposal lifecycle, then invoke the ordinary inconclusive timeout so it becomes UNCONFIRMED before the queued send/recovery rollback. Tick the READY manager. The item is retired without publishing its staged writes, but its input remains UTXO_RESERVED under the discarded transaction's reservation ID. Before this change, send rejection entered FAILED cleanup and released that reservation. The same skip occurs if timeout completes before the post-error RollbackTransactions call. No final certificate or consumed output is needed to reach this state.

**Fix:** Keep preservation of CONFIRMED effects and already-cleaned FAILED entries, but allow matching reservation cleanup for UNCONFIRMED transactions. Either narrow this private rollback preservation predicate or explicitly perform the non-final cleanup while retaining the expiry status. Do not broaden the wait-completion predicate or undo genuine certified effects. Add a deterministic ordinary-UTXO UNCONFIRMED regression using the existing timeout/rollback path; assert the exact reserved input becomes READY, its reservation is released, the nonce is reusable, no staged partner/sentinel is published, and a later genuine certificate can still apply normally. Retain the existing CONFIRMED/FAILED preservation twins.

**Evidence limit:** This is a static source trace. This reviewer did not modify tests or execute the reproduction.

### CR-01: Rejecting release decoders return successful null transactions to consensus — RESOLVED

**Classification:** BLOCKER  
**Resolution:** `7175219e3`

**File:** `/Users/henriqueklein/gnus/SuperGNUS/src/transaction/TransactionManager.cpp:2491-2496`  
**Related:** `TransactionManager.cpp:2484-2489`, `TransactionManager.cpp:2421`, `TransactionManager.cpp:2664`; `TransactionConsensusHandler.cpp:63-66`, `TransactionConsensusHandler.cpp:284-293`; `EscrowReleaseTransactionV2.cpp:85-136`.

**Issue:** The new V2 decoder deliberately returns `nullptr` for malformed shapes, such as an embedded tag-10 message with no hold input, a nonzero input index or an invalid output token length. The dispatcher returns that `shared_ptr` directly as `outcome::result<shared_ptr<GeniusTransaction>>`, which represents success even when the pointer is null. The production slot handler tests only `tx.has_value()` and immediately calls `tx.value()->GetSlotID()`. The nonce subject handler and raw transaction consumers likewise check only the outcome before dereferencing. The restored legacy decoder introduces the same interaction for rejected tag-7 payloads.

**Reachability:** A peer can sign an otherwise structurally acceptable consensus proposal whose nonce subject contains malformed V2 bytes. `ConsensusManager::HandleProposal` calls `GetSlotKey` while recording a proposal with unavailable registry evidence (`Consensus.cpp:2965-2983`) and on the ordinary known-registry path (`Consensus.cpp:3008`). `GetSlotKey` invokes the registered transaction slot handler before transaction-type admission can reject the malformed body. No payout certificate or quorum is needed for the null dereference. Raw CRDT release decoding also returns successful null values into `FilterTransaction`, which dereferences at `TransactionManager.cpp:4623`.

This dispatch contract weakness also existed for some older decoders; the phase adds two rejecting release codecs and a new wire case without adapting the boundary. The finding concerns those newly reachable release paths, rather than claiming the underlying generic weakness was first introduced here.

**Fix:** Normalize every manager decoding result at the owning dispatch boundary: a null pointer must become `std::errc::invalid_argument`, for both raw overloads and embedded dispatch. Preserve the dedicated codecs' nullable API if needed by their direct callers. Defensive pointer checks in the slot/nonce consumers should also prevent a future codec from recreating the crash. Add malformed V2 and legacy negative cases through the actual manager raw/embedded dispatch and production slot/nonce handlers, with a valid signed release as the positive twin; asserting only that the direct codec returns null does not cover this boundary.

**Re-review evidence:** `TransactionManager.cpp:2413-2428` now owns a single decode helper that rejects an absent codec or null result with `invalid_argument`. Both raw overloads (`2432-2436`, `2659-2666`) and all embedded cases (`2462-2521`) use it. The production slot and nonce consumers additionally guard the pointer (`TransactionConsensusHandler.cpp:63-69`, `284-288`). The malformed slot path falls back to the existing source/nonce identity without dereferencing; nonce admission rejects the malformed transaction. The fix does not change either codec or legacy tag-7/V2 tag-10 registration. `escrow_release_v2_test.cpp:928-1018` covers both raw overloads, embedded dispatch, actual slot/nonce handlers, and valid signed V2 plus both historical legacy fixtures with byte/hash/signature checks. These are source-inspected assertions, not a claim of test execution by this reviewer.

### CR-02: Pruning a paid hold permanently blocks payout replay and own-effect rollback — RESOLVED

**Classification:** BLOCKER  
**Resolution:** `661531ccc`

**File:** `/Users/henriqueklein/gnus/SuperGNUS/src/account/GeniusInputValidator.cpp:143-148`  
**Related:** `TransactionManager.cpp:3250-3253`, `TransactionManager.cpp:3316-3323`, `TransactionManager.cpp:2848-2855`; `src/transaction/PruneEligibility.cpp:489-581`.

**Issue:** `ResolveEscrowReleaseInput` requires the hold's mutable `tx/<hold-hash>` value before it can inspect the approved hold certificate. Every read failure returns `kNotSynced`; there is no recovery from the exact hold embedded in its permanent canonical certificate. Both V2 apply and V2 revert call this resolver before using genuine durable own-spender evidence.

**Concrete lifecycle:** Apply a valid V2 payout, retain its canonical certificate and genuine hold-spender record, and let the normal prune window elapse. `PruneEligibility::EvaluateCandidate` permits a hold whose produced outputs are all genuinely consumed with recorded spenders and sufficient age; it has no escrow exemption. The sanctioned erase removes the hold value while preserving certificates. After manager restart, duplicate certificate application or output rebuilding reaches `ParseEscrowReleaseTransactionV2`, receives `kNotSynced` and returns `invalid_argument` before `ApplyEscrowPayment` can restore the winner's outputs. The certificate handler remains retryable but cannot obtain a value intentionally removed by pruning. `RevertEscrowReleaseTransactionV2` also fails for this already-applied payment because the spender exists but the producer value is missing. The historical Transfer owner resolver similarly reads the raw hold value, so the same new requirement can strand legitimate legacy replay/rollback.

**Impact:** A supported storage lifecycle changes a valid paid transaction into an unreplayable transaction. In a rebuild with cleared recipient outputs, the genuine consumed hold survives while its recipient credits cannot be reconstructed. Even with outputs retained, restart cannot restore the payment's confirmed tracking state through this parser. This is distinct from a temporarily unsynced producer and from the explicitly deferred cross-era activation boundary.

The existing new prune test removes the **release** value while keeping the hold value. It therefore does not exercise removal of the producer required by the new resolver.

**Fix:** Recover the actual immutable hold from an approved canonical certificate when its raw value was legitimately pruned, selecting by the release's exact input transaction hash and retaining hash, dynamic type, output-zero, canonical slot and exact embedded binding checks. Reuse consensus-owned certificate validation and existing records; do not introduce a new authority store or trust uncle text. Share that producer recovery with historical escrow replay where applicable. Keep genuinely missing/deferred evidence pending and contradictory evidence invalid. Add a sanctioned **hold-prune** regression covering restart, exact winner output rebuild and own-effect revert, plus the foreign-spender negative twin proving recovery cannot authorize another payout.

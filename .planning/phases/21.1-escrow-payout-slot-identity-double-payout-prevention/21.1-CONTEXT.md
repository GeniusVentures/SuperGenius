# Phase 21.1: Escrow Payout Slot Identity & Double-Payout Prevention - Context

**Gathered:** 2026-11-20
**Status:** Ready for research and planning

<domain>
## Phase Boundary

Make proposals spending the same escrow for the same job compete under one canonical settlement identity regardless of submitting processor or nonce. Prevent conflicting payout finality and duplicate ledger effects, enforce durable input-conflict protection, and route duplicate certificates through the existing transaction machinery without endless permanent-conflict retries. Prove this through the incident brief's A-E matrix, replay, restart, and synchronization cases.

This urgent v1.3 insertion follows Phase 21 and precedes Phase 22. Requirements PAYSAFE-01..05 remain the scope anchor. Duplicate certificate creation and duplicate financial credit are separate evidence claims; staging financial impact remains unproven.

</domain>

<decisions>
## Implementation Decisions

These explicit user decisions refine the preliminary incident brief and take precedence over its provisional design suggestions. In particular, any wording about an assigned payout processor in PAYSAFE-03 or the roadmap must not become a designated-settlement-submitter restriction: assignment belongs to subtask execution; any processor may submit the complete validated settlement.

### Settlement boundaries

- **D-01:** One escrow funds exactly one job containing its subtasks.
- **D-02:** One final settlement per escrow distributes the payout to all entitled recipients. Partial/incremental settlements and multiple jobs per escrow are not the requested model.
- **D-03:** Settlement waits for every required subtask's result. Incomplete work does not trigger payout; cancellation/timeout-based early settlement is not added in this phase.
- **D-04:** Each subtask is assigned to and processed by one peer. Do not introduce replicated processing, a redundant-worker agreement threshold, or a requirement to collect results from several workers for the same subtask. Phase 26's later verification work must not be imported as the current execution model.

### Payout authority and existing processing behavior

- **D-05:** Any processor possessing the complete validated results may submit the final payout. The submitting processor has no authority to change entitled recipients or amounts. Different submitters still propose alternatives for the same job/escrow settlement.
- **D-06:** Preserve and reuse the existing subtask locking, expiration, and takeover behavior. The user specifically rejected designing a new assignment/failover policy: a peer locks a subtask and processes it through the current mechanism.
- **D-07:** Validate the result-to-job, executor/ownership, recipient, and amount bindings required for a legitimate payout. The exact authoritative evidence source and checks are research tasks; do not assume that a self-asserted result is sufficient or substitute a submitter allowlist for result validation. Coordinate this minimal safety binding with Phase 26's MINT-01/GRID work without marking those broader requirements complete.

### Duplicate certificates and permanent conflicts

- **D-08:** Treat creation of competing certificates for the same job as the defect. Reuse the existing transaction duplicate-certificate and conflict-handling path; do not add a special escrow quarantine policy or a node-wide payout pause policy.
- **D-09:** Connect escrow/job identity to the whole generic path: arbitration, durable voting, certificate publication/storage/lookup, transaction conflict detection, application, replay, restart, and sync. Changing only a displayed slot ID is insufficient if sender/nonce-based conflict lookups still miss the duplicate.
- **D-10:** Retain PAYSAFE-04's durable conflict evidence and termination of permanent application retries, using/extending the existing machinery as necessary. Preserve finalized spends and transient dependency recovery. Reusing current certificate ordering does not by itself prove input exclusivity or at-most-once application; research and tests must establish both.
- **D-11:** The user's statement that a created certificate has already validated rejects the proposed new operational policy. It does not request removal of normal signature, key-binding, registry, or quorum verification when receiving certificates.

### Upgrade expectations

- **D-12:** Use a coordinated validator upgrade: every validator receives the fix before the new payout rules activate. Supporting continued escrow settlement across mixed old/new validator rules is not required.
- **D-13:** Research/planning defines the activation and compatibility mechanics. Existing legitimate history and pending work need an explicit disposition; coordinated upgrade does not authorize resetting databases, erasing history, or deploying changes.

### Research and planner discretion

No specific algorithm, new library, or implementation layout was selected by the user. Research/planning must resolve canonical encoding, transaction/certificate identity plumbing, atomic input vote reservations, safe lock release and liveness, permanent-conflict journal integration, and activation/cutover details within the decisions above. These technical details must be grounded in the existing code rather than presented as new product-policy questions.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- `ProcessingSubTaskQueue::LockItem` records a node owner and expiration; `UnlockExpiredItems` clears expired locks through existing queue ownership rules. Preserve the behavior, while retaining appropriate evidence validation for payout.
- `GeniusNode::ProcessingDone` completes a task and calls `AsyncPayEscrow` with its result and CRDT transaction.
- `TransactionManager::PayEscrow` consumes escrow output 0 and uses `BuildPayoutOutputs` to construct one transfer with multiple entitled outputs. The submitting account currently signs and supplies DAG metadata.
- `PersistOrLoadExactActiveVote` already persists an active vote by slot before publication. Reuse its durability pattern while researching the required all-input conflict protection.

### Established Patterns

- `SubmitCertificate` and `FilterCertificate` address certificates through canonical keys and use serialized-certificate-hash ordering to converge competing stored records. Reuse generic certificate handling; establish with tests how it interacts with irrevocable transaction application.
- `GetConflictingTransactions` currently compares sender/nonce, while `HasConfirmedInputConflict` only scans confirmed tracked transactions. Both are integration concerns for cross-processor escrow competitors.
- `AddTransactionToProcessedMaps` rejects a new conflicting transaction when a recognized competitor is already confirmed. Confirm the same-job identity reaches this path rather than inventing an independent payout registry with divergent rules.

### Integration Points

- End-to-end identity: escrow/job facts -> transfer slot -> proposal/certificate key -> certificate matching/lookup -> transaction conflict detection -> ledger application.
- Durable input reservation and release across approval, certification, crashes, and multi-input overlaps.
- Certificate-work journal outcomes: permanent duplicate/conflict completion versus retryable missing dependencies.
- Coordinated activation and historical/pending transaction replay; no live mixed-rule settlement requirement.

</code_context>

<specifics>
## Specific Ideas

- The user's clarification was: a subtask is assigned to and processed by just one peer; the existing system lets a peer lock it and continue processing. Do not ask the user to design a replacement for this.
- The user explicitly requested handling duplicated job payout certificates like duplicated certificates on transactions. The phase fixes missing competitor identity and input safety while reusing that generic behavior.
- Retain incident tests A-E, baseline/fixed build provenance, registry CID/epoch and active weights, exact signed votes, spent outpoints, and final per-node balances. Certificate safety and financial at-most-once behavior must be asserted separately.
- Dominating Byzantine quorum weight is outside an honest-validator locking guarantee. Weight redistribution alone is not a fix for the cross-slot identity issue.

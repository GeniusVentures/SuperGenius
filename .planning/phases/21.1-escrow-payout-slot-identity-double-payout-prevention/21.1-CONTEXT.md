# Phase 21.1: Escrow Payout Slot Identity & Double-Payout Prevention - Context

**Gathered:** 2026-11-20
**Status:** Ready for planning; scope corrected after user clarification

<domain>
## Phase Boundary

Fix the Slot ID mismatch when two different peers submit payouts for the same job escrow. Follow the existing Mint pattern: transaction-specific GetSlotID() derives identity from the shared underlying event, rather than the proposing peer's source address and nonce. Same job escrow -> same consensus slot -> existing arbitration and duplicate-certificate handling.

Implement this through a dedicated **EscrowReleaseTransaction** for job escrow payouts. It owns the canonical Slot ID and the escrow-specific spend rules. Replace the current payout-as-transfer path and remove the delegated escrow-spend exception from ordinary transfer validation for newly admitted transactions, with an explicit historical replay/cutover policy.

This is a focused escrow payout identity fix, not a new payout authorization system, processing-assignment system, general all-input reservation protocol, or certificate-recovery framework. Verify the full existing identity path and change only the integration needed for the canonical slot to work correctly.

The user explicitly corrected the earlier context: "The issue is with Slot ID not being the same for 2 different peers trying to payout the same job escrow. We have to do something like what it's done on Mint." This clarification supersedes the initial incident report's candidate fixes and the assistant's broader interpretation. Staging duplicate financial credit remains unproven.

</domain>

<decisions>
## Implementation Decisions

### Primary fix: follow Mint
- **D-01:** Two different peers attempting to pay the same job escrow must get the same Slot ID despite different sender addresses, nonces, proposal envelopes, signatures, and transaction hashes. Different job escrows must get distinct slots.
- **D-02:** Use the existing transaction-specific Slot ID mechanism, like MintTransactionV2::GetSlotID(), on a dedicated EscrowReleaseTransaction. Derive the escrow payout slot from stable, verifiable escrow/job identity; the escrow transaction hash and spent output index are the concrete existing facts to investigate. Exact canonical encoding remains a planning detail; do not implement the fix as another escrow special case inside ordinary TransferTransaction.
- **D-03:** Reconstruct the same slot from serialized/embedded transactions on every peer. Do not use an ephemeral local-only override, an unverified claimed job ID, or mutable payout contents that let a competitor evade the shared slot.
- **D-04:** Reuse the current consensus slot arbitration, active-vote persistence, certificate storage/lookup, and duplicate transaction/certificate behavior. Keep exact certificate-to-transaction binding: sharing a slot must not let the losing payout use the winner's certificate to confirm.
- **D-05:** Check the existing end-to-end path for sender/nonce assumptions that bypass the corrected identity. Make only the corresponding integration fixes needed for escrow payouts. Do not presume changing one return value is sufficient without tracing and testing the actual payout proposal/certificate/application path.

### Existing behavior to preserve
- **D-06:** One escrow funds one job; one final settlement covers all entitled recipients after every required subtask has returned its result.
- **D-07:** Each subtask is processed by one peer through the existing locking, expiration, and takeover mechanism. Preserve that mechanism; do not introduce replicated work or design a replacement assignment policy.
- **D-08:** Any processor with the complete validated results may submit the payout. Do not introduce a designated settlement processor or submitter allowlist. Existing result/payout checks remain; redesigning their authority model is outside this focused fix.
- **D-09:** Handle duplicate certificates as existing transactions do. Do not invent escrow quarantine, node-wide payout pauses, a separate settlement-finality registry, or a new recovery policy.
- **D-10:** Use a coordinated validator upgrade, with all validators fixed before activation. Preserve legitimate historical replay and define any necessary pending-work/cutover handling during planning. No deployment or database reset is authorized.

### Scope control and planner discretion
- **D-11:** Do not make general cross-slot all-input vote reservations, new processor-assignment authorization, a new permanent-conflict journal, or validator-weight changes mandatory work for this phase. These came from the preliminary assessment, not the user's clarified fix.
- **D-12:** Research/planning owns canonical encoding, correct dedicated-type integration, regression layout, and coordinated activation details. If a separate defect blocks this targeted fix, document concrete evidence and its dependency rather than silently broadening the phase.

### Dedicated escrow-release transaction (user refinement)
- **D-13:** Create a real EscrowReleaseTransaction for the final job payout, owning its GetSlotID() override, serialized and embedded representation, deserializer, signing/hash behavior, validation dispatch, apply/revert handling, topics, and necessary existing payout/status integration. Reuse established transaction patterns and payout-output construction; do not duplicate the consensus framework.
- **D-14:** Ordinary transfers use normal input ownership rules. Move the escrow-specific spending rule out of the generic delegated-escrow exception and into explicit escrow-release validation. A release type tag alone must not authorize arbitrary non-owned inputs: bind the claimed escrow to the actual consumed escrow hold/outpoint and retain existing signature, spend-state, amount/token, and payout checks. This does not restrict submission to a designated processor or introduce Phase 26's broader authority redesign.
- **D-15:** PayEscrow must create the dedicated release type. The existing EscrowTransaction continues to represent escrow holds; the existing TransferTransaction continues to represent ordinary transfers. Both existing Mint identity and exact transaction-certificate binding stay intact.
- **D-16:** Existing scaffolding is incomplete: SGTransaction.proto defines EscrowReleaseTx and Consensus.proto already has an escrow_release oneof field, but TransactionManager's escrow-release deserializer currently maps to EscrowTransaction::DeSerializeByteVector and its parser table lacks an escrow-release handler. Inspect and complete this wiring rather than assume a functional release type exists. Preserve protobuf field numbers and assess the existing release_amount/release_address fields against the required multi-recipient final payout before extending the schema.
- **D-17:** Tests must prove cross-peer canonical release slots, release roundtrip/embedded reconstruction and correct dynamic type, winner-only certification/application, ordinary-transfer rejection of the removed escrow bypass after activation, invalid claimed/non-escrow release input rejection, and valid release payout contents. Plan historical legacy-transfer payout replay and pending-work cutover explicitly; removing the active bypass must not silently erase or invalidate legitimate old history.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- MintTransactionV2::GetSlotID() already demonstrates proposer-independent transaction identity.
- TransactionConsensusHandler::RegisterSlotKeyHandler already routes embedded transactions through their virtual GetSlotID(); no new generic slot dispatch framework is needed.
- PayEscrow has stable shared input facts: the escrow transaction hash and output index 0. Its current transfer receives peer-specific DAG metadata, exposing the inherited sender/nonce identity mismatch.
- A wire-level EscrowReleaseTx and embedded escrow_release case already exist, but their alias to the hold deserializer is incomplete scaffolding. The dedicated class and actual lifecycle must be wired end to end, including the parser table and relevant transaction-type checks.
- Existing canonical certificate storage and exact transaction binding should handle the competitors once the payout identity is consistent.

### Established Patterns
- Same underlying event -> same transaction-specific slot, even when the transaction hashes and proposing peers differ.
- Shared slot -> common arbitration/certificate handling; a certificate remains bound to its actual winning transaction.
- Ordinary transfers and Mint keep their existing identity rules. A dedicated release type carries verifiable escrow facts and the canonical payout identity; it is not an ordinary transfer recognized by a local flag or an ownership exception.

### Integration Points
- Payout creation -> serialized transaction -> GetSlotID() -> NONCE_SUBJECT slot handler -> vote/arbitration -> canonical certificate key -> certificate matching/application.
- New release type -> correct deserialization/embedded dispatch -> dedicated escrow input validation -> apply/revert and status tracking; historical transfer-payout compatibility is separate from new release admission.
- Trace sender/nonce conflict lookups where relevant to ensure they do not bypass the canonical payout identity.
- Regression: two peers, same job escrow, different nonces/hashes -> equal transaction slots and equal consensus/certificate slots; different escrows -> unequal slots; one winner pays once across replay/restart.

</code_context>

## User's Clarification

The user specifically wants the equivalent of what Mint does for competing peers, applied to job escrow payouts. Start with Mint's GetSlotID() and its existing cross-proposer slot and exact-certificate-binding tests. Do not turn the preliminary report's four proposed fixes into a mandatory consensus redesign.

The user then proposed a new transaction type for escrow-release payment, replacing the current transfer "hacked to allow for UTXOs being escrow holds." The dedicated transaction is the chosen implementation direction, so it can own these rules without extending the ordinary-transfer workaround.

Retain the incident A-E validator configurations and evidence capture as relevant reproduction/validation inputs. Weighted quorum changes or other incident investigations are not the implementation mechanism for this Slot ID fix.

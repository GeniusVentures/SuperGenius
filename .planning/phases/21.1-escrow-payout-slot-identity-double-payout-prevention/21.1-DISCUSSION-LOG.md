## Implementation refinement: dedicated escrow-release payment transaction — 2026-11-20

**User proposal:** "we should probably create a new type of transaction of payment on escrow release, which now is just a transfer that is hacked to allow for UTXOs being escrow holds. I think that would remove the hack and make it easier to implement these new rules"

**Design captured:** A dedicated EscrowReleaseTransaction owns its Mint-style canonical Slot ID and escrow-specific spend validation. PayEscrow constructs this type; ordinary transfers return to normal input ownership checks for new admission. Preserve existing subtask assignment, payout distribution, any-processor submission, generic certificate arbitration, and coordinated-upgrade decisions. Plan legacy transfer-payout history and pending-work compatibility explicitly.

**Source findings:** SGTransaction.proto already defines EscrowReleaseTx and Consensus.proto contains escrow_release oneof tag 7. There is no corresponding C++ release class in the current source; TransactionManager registers escrow-release using EscrowTransaction::DeSerializeByteVector, and its parser table lacks escrow-release. Implement the actual type and correct the complete serialization/deserialization/validation/apply/revert/status path, rather than assume the scaffolding is functional. Generic UTXOManager::VerifyParameters currently contains the delegated-escrow ownership exception; isolate that rule behind the real release type and validate the actual escrow input rather than trusting its claimed type alone.

## Historical explanation and V2 payment semantics — 2026-11-20

**User clarification:** "That partial scaffolding was due to a previous version that didn't do much except check when the payout was processed, so the plan is to implement the V2 version that behaves like the transfer of funds but has a dedicated transaction to it, which also solved the slot ID issue"

**Decision:** Implement EscrowReleaseTransactionV2 as the actual funds-moving transaction with transfer-like UTXO consumption and recipient output creation, plus the Mint-style canonical escrow Slot ID. The previous release/status-check version is legacy context, not a partially implemented V2 payment. Preserve its wire fields/tags and interpretation; plan explicit versioned V2 representation and dispatch. Reuse the current payout distribution and UTXO machinery rather than emit a transfer plus a marker or redesign payout policy.

**Acceptance clarification:** Verify actual escrow input consumption, recipient UTXOs/balance effects, shared cross-peer Slot ID, winner-only payment, and replay at-most-once behavior. A processed-payout status check alone does not prove V2 executes the payment.

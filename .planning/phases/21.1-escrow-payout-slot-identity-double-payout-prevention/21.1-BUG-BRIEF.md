The user clarified: "The issue is with Slot ID not being the same for 2 different peers trying to payout the same job escrow. We have to do something like what it's done on Mint."

The implementation phase therefore targets a Mint-style, proposer-independent escrow payout Slot ID and the minimal existing-path integration needed for generic arbitration, certificate binding, and duplicate handling to recognize the competitors. The broader candidate fixes below are retained as the original preliminary assessment, not as mandatory implementation deliverables. Do not add a general all-input reservation protocol, new processor-assignment policy, or new certificate-recovery framework on that basis. See `21.1-CONTEXT.md` and the corrected PAYSAFE requirements for the authoritative phase scope.

Confirmed discussion behavior: one escrow funds one job; one final payout follows every required subtask's result; each subtask uses the existing one-peer lock/takeover mechanism; any processor may submit the complete validated payout; duplicate certificates follow existing transaction handling; activation uses a coordinated validator upgrade.

**Subsequent implementation direction:** The user proposed a dedicated escrow-release payment transaction instead of the current transfer ownership exception. Implement a real EscrowReleaseTransaction with its own Mint-style GetSlotID and escrow-specific validation, wire PayEscrow to create it, and restore ordinary transfer ownership checks for newly admitted transactions. Existing EscrowReleaseTx/embedded wire scaffolding is incomplete: the release deserializer currently points to the escrow-hold class. Audit and complete it while preserving wire numbering and explicitly handling legacy payout replay/cutover. This is the targeted way to implement the slot fix, not a new processor-assignment or generic consensus redesign.

## Problem and evidence boundary

Two processors can reportedly propose payouts spending the same escrow output while obtaining different sender/nonce-based consensus slot IDs. Slot-local arbitration and vote persistence therefore need not recognize the transactions as competitors. This is a potential production double-spend and consensus-safety defect, independently of staging's unusual voting-weight distribution.

The user reports two payout certificates in staging. Neither certificate, the exact staging binaries, registry history, nor final ledger credits has been independently recovered for this phase. Two valid conflicting certificates and two completed payments are separate claims. Existing consumed-input checks can reject the second transaction during local ledger application. Do not describe duplicate financial credit as established or mark this phase complete from local rejection alone.

The local checkout matched the full baseline SHA when this brief was written. The source mechanisms below were spot-checked directly. No staging reproduction or new test execution was performed during phase creation, and local HEAD does not establish the current remote branch or staging deployment version.

## Reported staging weight imbalance

Reported weight: one processor has 50,000 of 50,047 total voting weight, approximately 99.906%. It can exceed a two-thirds threshold alone. Confirm the actual threshold, registry CID/epoch, active status, role, weight overrides, and certificate-time membership from evidence.

Under the default weights, two active genesis validators in the same registry contribute 100,000 before other validators. A reported total of 50,047 does not match that configuration. Investigate whether the second genesis belongs to another registry, is inactive, has overridden weight, or never joined. Do not infer the registry population solely from the total weight.

Balanced weights do not repair missing conflict identity: honest validators may approve both transactions if each appears acceptable in a different slot. Under a two-thirds rule with four equal validators, three validators could approve each transaction when cross-slot input conflicts are not recognized.

A Byzantine actor controlling sufficient quorum weight can violate certificate exclusivity independently of this bug. State the threat model explicitly; do not promise that an honest-voter input lock constrains a malicious quorum. Test dominating-weight configurations with conforming voters and document malicious-quorum limits separately.

## Required outcomes and candidate mechanisms

These are requirements and proposed approaches supplied by the user, not a finalized implementation design.

1. **PAYSAFE-01 — Canonical settlement identity.** Competing processors address the same logical escrow settlement through one consensus decision. Bind the identity to stable escrow/job facts rather than proposer identity. Define settlement granularity and distinguish legitimate separate payouts. Existing `BestHash` arbitration is slot-local and cannot alone resolve cross-slot conflicts.
2. **PAYSAFE-02 — Durable input protection.** Persist a validator's input-outpoint reservation before publishing approval. Reject conflicting pending spends regardless of sender/nonce. Acquire and resolve every input of a multi-input transaction together. Specify crash atomicity, replay, lock release, competing rounds, ordering/deadlock avoidance, and recovery so a failed proposal cannot permanently strand funds or enable later equivocation.
3. **PAYSAFE-03 — Payout authority and contents.** Verify processor assignment, authorized failover, and recipient/amount binding to the authoritative certified work result before certification and application. Missing evidence fails closed. Identify the existing authoritative result source; if absent, define a safe gate rather than accepting a self-asserted result.
4. **PAYSAFE-04 — Permanent certificate conflicts.** Distinguish a finalized competing spend from a transient missing dependency. Stop endless retries for permanent conflicts, retain both certificates/votes/registry identities/outpoints for audit and recovery, and preserve finalized state. Define operator-visible status and recovery policy; never silently discard evidence or undo a finalized payment.
5. **PAYSAFE-05 — Multi-node safety and convergence proof.** Use real vote, certificate, persistence, application, and synchronization paths with reproducible fault injection and explicit quorum assumptions. Prove certificate exclusivity and ledger at-most-once behavior separately, plus progress after recoverable faults.

## Reproduction and acceptance matrix

First capture behavior using unmodified binaries built from the baseline SHA. Then rerun the same scenarios on the fixed revision, recording both build identities. The baseline may demonstrate failures; fixed-build acceptance requires the safety outcomes below.

| Test | Validator setup / fault | Required fixed-build result |
|---|---|---|
| A | One active genesis at 50,000 weight, reported additional weight reproduced | Conforming validators certify at most one conflicting payout; a valid authorized payout eventually completes when dependencies and communication are available. |
| B | Two active genesis validators at 50,000 each in the same registry | At most one conflicting payout certifies; both memberships and active weights are captured. |
| C | Four equal-weight validators | Honest votes cannot form conflicting valid certificates for the same settlement/input; at most one ledger effect. |
| D | Four equal-weight validators, delayed/reordered votes and network partition | Safety holds under the documented fault bound, without requiring progress in a partition lacking quorum; after healing, nodes converge and legitimate work progresses. |
| E | Restart and synchronize after competing payout attempts | Durable reservations and accepted finality survive; nodes converge on spent outputs and balances without duplicate credit or endless retries. |

Additional mandatory cases: overlapping multi-input sets across different slots; crash between lock persistence and vote publication; concurrent approval attempts; authorized processor failover; unauthorized processor and altered payout recipients/amounts; certificate replay/catch-up; transient dependency recovery versus permanent finalized-input conflict; compatibility with existing legitimate history and non-escrow transactions.

For each candidate/certificate, capture:

- Binary/build SHA, configuration, network identity, processor identities, transaction bytes/hash, proposed slot/settlement identity, and every input outpoint.
- Registry CID, epoch, active membership/roles/weights, quorum policy/threshold, exact signed vote set, and certificate-validation verdict.
- Certificate acceptance versus application/retry/terminal status on each node; final spent state, recipients, amounts, and balances.
- Whether purported competing certificates refer to the same authorized registry or different registry histories, with evidence validating any registry transition.

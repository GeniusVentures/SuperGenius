## Critical Integration Gaps

### 1. Production TrustedPeerRegistry genesis is never seeded or confirmed

`TrustedPeerRegistry::New` populates an in-memory cache but does not create the signed genesis CRDT record. The real startup path constructs the registry and proceeds without calling `SeedGenesis()` or `TryConfirm()`.

The current `example/node_test/sgns_config.json` addresses are not the final project trusted peers. Before release, operators must manually collect the real peer public addresses, verify them out of band, choose the thresholds, canonicalize the list, and distribute one identical authenticated genesis artifact to every node. That ceremony and its expected output are not currently documented or enforced.

Consequences:

- TPR remains authorized by the single bootstrapper instead of the confirmed current peer quorum.
- BurnConfig consumes a locally configured, unconfirmed peer cache as its signer set.
- The component-level genesis test does not represent the running product flow.
- Mutable JSON—not a signed or pinned manifest—is currently the pre-confirmation trust root.

Affected requirements: **TPR-01, TPR-02, SCRDT-04, BURN-01**.

### 2. Live update operations are orphaned from the product

TrustedPeerRegistry's propose/sign/confirm methods are only called by tests. BurnConfig exposes no equivalent update/sign surface, and GeniusNode provides no facade or RPC path to its private SecureCrdt, TrustedPeerRegistry, or BurnConfig instances.

Consequences:

- A running node cannot initiate or sign membership changes.
- A running node cannot initiate or sign burn-rate changes.
- The milestone's live-update behavior exists as library capability, not product capability.

Affected requirements: **SCRDT-04, TPR-02, BURN-01, BURN-02**.

### 3. Burn refresh callback is lost after account selection

`SelectAccount()` retains the existing GlobalDB while destroying and recreating BurnConfig. The old GlobalDB callback remains registered with an expired weak pointer. Registration of the same pattern for the new instance is rejected, and the result is ignored.

Consequence: quorum-signed burn changes stop refreshing TransactionManager after account selection.

Affected requirement: **BURN-02**.

## Trust-Bootstrap Threat Assessment

The concern about a bad actor overwriting `sgns_config.json` is valid.

Current behavior:

- `GeniusNode::LoadSgnsConfig()` accepts `trusted_peers`, `bootstrapper_node`, `trusted_peer_quorum_threshold`, and `burn_config_quorum_threshold` directly from the JSON.
- `TrustedPeerRegistry::New()` immediately copies that peer list into `cached_peers_`.
- Before signed genesis confirmation, `ResolveSignerSet()` trusts the configured bootstrapper alone at threshold 1.
- `BurnConfig` uses `TrustedPeerRegistry::GetCurrentPeers()` even when `IsGenesisConfirmed()` is false.
- No manifest hash, offline-root signature, network identity binding, or comparison against a previously confirmed genesis value protects these fields.

Impact depends on attacker capability:

| Attack | Likely effect |
|--------|---------------|
| Change JSON without possessing any listed private key | Loss of quorum or rejection of legitimate signatures; node startup/operation denial and state divergence |
| Replace the list with attacker-controlled addresses and matching keys | Local trust-root takeover; the node can accept attacker-authorized registry and BurnConfig values once the update path is operational |
| Compromise the deployment artifact used by many/all nodes | Network-wide trust-root takeover rather than a single-node divergence |
| Change thresholds only | Lowering below the computed majority floor is rejected, but a one-member attacker list with threshold 1 passes; thresholds above member count are currently accepted and create permanent denial of quorum |

BurnConfig restricts values to 0–10,000 basis points, but within that range a successful signer-set takeover could authorize economically destructive policy, including a 0% or 100% burn rate. Today the missing production update ingress limits immediate exploitability, but that same ingress is required to finish the milestone; the trust bootstrap must be fixed before exposing it.

Required secure bootstrap:

1. Produce a canonical genesis manifest containing network ID, ordered unique peer addresses, membership threshold, burn threshold, version, and manifest hash.
2. Have operators verify the addresses through an out-of-band ceremony and publish the expected manifest hash through a separate trusted channel.
3. Authenticate the manifest with a pinned hash or offline-root signature; JSON may locate the manifest but must not define authority by itself.
4. On first boot, verify the manifest, submit and confirm the signed genesis record, then persist the confirmed genesis hash/state.
5. On later boots, load the confirmed state and fail closed if local configuration attempts to replace the genesis trust root.
6. Validate non-empty unique addresses and enforce `1 <= threshold <= signer_count` in addition to the majority floor.
7. Protect configuration files and deployment artifacts with least-privilege permissions and integrity monitoring as defense in depth.

## Recommended Closure Work

Group the three related product-integration blockers into a single closure phase:

1. Define and document the manual trusted-peer address collection, verification, threshold-selection, and genesis-manifest ceremony; clearly mark the current JSON addresses as non-production placeholders.
2. Authenticate and pin the canonical genesis manifest so mutable JSON cannot redefine the trust root.
3. Complete and verify production TPR genesis seeding/confirmation, persisting and checking the confirmed genesis identity on later boots.
4. Add an authorized operational surface for trusted-peer and burn-rate propose/sign/confirm flows.
5. Make CRDT callback registration lifecycle-safe across `SelectAccount()` and multi-node instances.
6. Add real product-level E2E and tamper tests covering startup genesis, altered JSON, manifest mismatch, membership update, live burn update, account selection, and `PayEscrow` consumption.
7. Reconcile MIG-05 wording and stale requirements/summary metadata.

Also run Nyquist remediation for Phases 8 and 12 before milestone closure.

Milestone v1.1 should not be archived as fully complete yet. Its low-level primitives are substantial and mostly verified, but the core product promise—quorum-controlled live CRDT configuration in a running node—is not end-to-end operational.
